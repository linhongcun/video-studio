# 图文文章结构调研与重构方案

2026-11-03完成资料调研与项目样本审阅。本方案供后续改稿使用，包含文章分类、组成结构、三篇改稿样例与验收方法；当前线上文章保持v0.99.2，本轮未替换发布稿。项目基线为 `058890d1e2c995ad5c2e2e02e34a02652886bcb6`。

建议将文章组织为一条读者可以跟随的问题链：先说明值得解决的问题与阅读所得，随后沿具体例子逐步解释关键关系，最后让读者能回答原问题、识别结论的适用条件。完整实现、长证明和实验记录按用途分层，核心因果和必要的正确性依据留在主线。篇幅和章节数随内容决定。

## 值得借鉴的写作经验

### 开头交代问题和阅读所得

Google的技术写作课程建议用引言建立目的、读者与范围；GOV.UK强调重要信息前置，并让摘要与开头承担不同职责。用于我们的解释文章，可以先给出具体问题与一句核心方向，再由正文展开原因。[Google](https://developers.google.com/tech-writing/two/large-docs)、[GOV.UK](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/clear-structure/)

例如消费幂等篇，开头即可点明“积分事务与Kafka恢复位点分别提交”，随后解释故障怎样使同一条事件重来。读者先知道这篇文章要解决什么，继续阅读是为了理解因果与判断条件。查答案的参考文可以更早给出结果；推导文章则保留必要的探索过程。

### 正文按读者的问题推进

Diátaxis将面向理解的解释文，与带读者完成操作的教程区分。前者需要原因、联系和取舍，后者强调连贯行动与可见结果。我们的原理篇应把“为什么会发生、谁保存状态、条件变化会怎样”串起来，实操篇才围绕动作和输出组织。[Explanation](https://diataxis.fr/explanation/)、[Tutorials](https://diataxis.fr/tutorials/)

每节应使读者多解释清楚一件事，并给下一节留下自然的问题。章节名称优先表达它解决的具体疑问；短文中连续动作可用同一章内的小节或步骤表示，避免每句话都变成一个主章节。

### 先给可理解的例子再建立抽象关系

Julia Evans总结的常见解释问题包括抽象起步、预设知识不一致、一次引入过多概念，以及只列功能却不解释原因。3Blue1Brown的微积分文字课则从圆面积这个具体问题，逐步建立更一般的关系。前者是作者经验，后者是可观察的写作案例；两者都能帮助我们检查例子与术语的出场顺序。[Julia Evans](https://jvns.ca/blog/confusing-explanations/)、[The Essence of Calculus](https://www.3blue1brown.com/lessons/essence-of-calculus/)

同一订单、数组或楼层实例可以贯穿主线。对象建立后，再引入它对应的术语与实现。若用一个会失败的办法引出推导，先说明它是假设、对照或待检验的尝试，让读者知道正在分析什么；推导不需要每篇都安排错误方案。

### 配图参与解释而且紧邻对应文字

IES实践指南建议连接图与文字、具体表示与抽象表示；Red Blob Games的作者实践展示了图、代码和文字之间的一致标记，也强调局部交互应能独立理解。用于我们的图文，应在当前段落指出图中要观察的对象、变化与结论，再接上相关代码或规则。[IES指南](https://ies.ed.gov/ncee/wwc/Docs/PracticeGuide/20072004.pdf)、[Little Design Things](https://www.redblobgames.com/making-of/little-things/)

已有图能说明一次排除，就放在第一次解释这次排除的位置附近；图片数量本身不能说明教学是否清楚。静态图已经能表达关系时可以继续使用，交互仅在读者改变条件有助于判断结果时考虑。

### 同时支持顺着读和按需深入

NN/G对在线阅读的研究总结指出，阅读方式会随任务、动机和个人情况变化。文章需要清楚的标题与定位入口，也要有连续可读的论证。[How People Read Online](https://www.nngroup.com/articles/how-people-read-online/)

主线优先回答标题的问题；完整代码、深入源码、形式化拓展和实验复现可以明确标注用途并提供入口。必要的推导、正确性依据以及会改变结论的前提仍留在相关正文附近。制作镜号、编码检查、验证工具的过程记录可链接到工程资料，正文保留其对结论可信范围有实际影响的信息。

### 自检与结尾总结

IES指南对深层解释性问题提供较强的证据支持；Roediger与Karpicke的实验研究区分了回忆尝试与重复阅读。对我们可尝试的做法是：长文在小结前用一个条件变化问题检查关键关系，并提供答案或推理线索，然后在小结中收回原问题。[IES指南](https://ies.ed.gov/ncee/wwc/Docs/PracticeGuide/20072004.pdf)、[Test-Enhanced Learning](https://learninglab.psych.purdue.edu/downloads/2006/2006_Roediger_Karpicke_PsychSci.pdf)

例如“数据库成功但位点未提交，恢复后怎样；若先提交位点又怎样”。它要求读者解释机制，而非仅认出术语。短文无需为了形式增加习题；现行小结仍放在全部正文及必要拓展之后、参考资料之前。

## 不同文章的组成结构

下表是结合来源和项目内容形成的编辑方案，表示内容功能和推进关系，不要求对应固定数量的二级标题。

| 文章类型 | 建议主线 | 适合分层的内容 |
| --- | --- | --- |
| 原理与机制，包括设计模式 | 具体问题或异常现象 → 核心解释方向 → 同一案例中的动作与状态 → 为什么这样设计 → 条件变化与取舍 → 小结 | 深入源码、完整配置、复现步骤；改变结论的边界留在相关正文 |
| 算法 | 输入条件与返回目标 → 已有信息能省掉什么尝试 → 关键关系与不变量 → 完整走例 → 正确性及边界 → 代码与复杂度 → 小结 | 额外实现、长穷举记录；核心排除依据不能移走 |
| 逻辑推理 | 规则和目标 → 明确标记的尝试 → 找到限制与资源预算 → 构造可行方案 → 判断是否最优 → 小结 | 扩展变体、完整状态枚举；可行性和最优性的区别必须讲清 |
| 动手教程 | 完成目标和最低前提 → 最小行动路径 → 每步预期结果与观察点 → 常见失败与恢复 → 完成结果和下一步 | 原理深挖与备选配置；执行所需的安全条件和前提就近给出 |

首段可用具体问题建立入口，再用一句话交代读完能解释什么。长文随后提供阅读路线；短文可以直接进入主线。每节围绕当前问题组织例子、解释和图示，顺序由论证需要决定。必要拓展结束后用小结明确答案、关键关系与适用条件，最后列参考资料。

## 项目样本中的结构观察

抽样覆盖DNS、HTTP请求、消费幂等、适配器、二分查找、每日温度、两枚鸡蛋和三门问题。[逐篇审阅记录](project-audit.json)保留源稿SHA、观察、应用推断、保留项与锚点映射。观察来自MDX与相关页面代码审阅，不能代替读者阅读测试。

| 样本 | 已有优点 | 优先调整 |
| --- | --- | --- |
| DNS短文 | 查询链条单一，有缓存与TTL边界 | 首段明确同一示例名字和地址；合并碎片化小节，在一章内走完根、顶级域、权威的转介链 |
| HTTP请求 | 有具体请求响应与TCP/TLS/HTTP职责 | 让读者先识别整条主线，再按需读报文细节；版本对照服务于具体问题 |
| 消费幂等长文 | 同一E01贯穿，分清恢复位置与业务结果 | 核心故障窗口尽早清楚；将完整数据库实现和复现细节标出深入入口 |
| 适配器长文 | 业务约定和供应方边界具体 | 让完整请求及返回的关系先闭合，语言与SDK细节按需深入 |
| 二分查找 | 已解释安全排除与闭区间不变量 | 将排除图贴近首次排除解释；制作验收信息从主线分层 |
| 每日温度 | 从等待需求推导到单调关系与栈 | 保留推导，集中图和状态对应；把镜号、代码显示与核验数量链接到复现记录 |
| 两枚鸡蛋 | 已从固定间隔推到预算，兼顾端点 | 明确区分构造可行、证明最优和程序核验三层用途 |
| 三门问题 | 固定规则下的分类推理清楚 | 主结论之后提供阅读分流，具体门号后验与盲开变体明确作为深入层 |

另有两项界面事实影响结构落地。文章的frontmatter/metadata摘要没有自动显示为正文引入，写好摘要不等于读者已经看见导读。侧栏目录来自带有文章映射的视频章节，新增的正文标题、小结和拓展不会自动全部出现。当前可在MDX正文写清引入及必要的阅读路线；若改共享目录，应把文章导航与视频回看对应关系分别处理和验收。

## 三篇改稿样例

以下为可执行的目录与开头试写，尚未替换现行发布文章。

### DNS短文

建议目录保留现有主要锚点：域名需要变成什么 `hook` → 先查可用缓存 `cache` → 解析器沿转介取得地址 `query` → 下一次能否复用 `ttl` → 小结 → 参考资料 `recap`。根、顶级域、权威与返回答案作为 `query` 内的步骤展开；它们的层级调整无需改变视频章的身份。

开头试写：浏览器拿到 `shop.example` 这个名字，还需要一个可连接的地址。假设浏览器、系统和递归解析器都没有可用缓存，接下来由谁把名字查成地址？我们沿同一次教学查询，看看解析器怎样取得转介、找到权威回答，并把示例地址 `203.0.113.10` 返回客户端。这个地址是教学设定，解析结束后仍要继续建立连接。

该示例值来自现有文章的来源说明；实际改稿时仍需对照当前配图，保持名字、地址与图注一致。

### 消费幂等长文

建议目录：一条E01怎样让积分从10变20 `problem` → 一次故障留下哪些不同状态 `positions` → 旧恢复位置怎样进入新读取请求 `replay` → 提前提交为何会漏做、业务键怎样保护效果 `guard` → 可选深入的数据库并发与复现 → 小结 → 参考资料。保留关键源码对应和引用在它实际支持的论点旁。

开头试写：生产者只写入一条积分事件E01，账户也已经加了10分，消费者重启后却可能再加一次。关键在于：数据库中的积分结果，与Kafka保存的恢复位置分别提交。沿同一条E01看清这个故障窗口，就能解释它为什么重来、提前提交为什么可能漏做，以及业务幂等究竟保护什么。

完整实现保留，主线先建立恢复与重复效果的因果。深挖入口应明确告诉读者它解决的是并发去重、事务边界还是实验复现，避免把所有细节都挤进第一次解释。

### 两枚鸡蛋推理文

建议目录：规则与失败后剩余资源 `rules` → 固定10层为什么最坏19次 `problem` → 怎样预留碎后的次数 `budget` → 用F为31走完一局 `example` → 为什么13次不能保证 `why-fourteen` → 可选程序与全阈值核验 `bounds` → 小结 → 参考资料。

开头试写：100层楼、两枚鸡蛋，要找到最高安全楼层。每次投掷不仅缩小答案范围，也可能消耗下一次试验要用的鸡蛋。只剩最后一枚且答案仍不确定时，就必须给逐层确认留出机会；本文从这条限制推导递减间隔，解释怎样保证14次以内完成，再说明为什么13次不够。

题目规则、F可取0和100、示例构造与最优性依据均保留。推导中的假设分支明确标记，避免读者把固定间隔当成最终推荐路线。

## 重构与验证顺序

先用DNS、消费幂等、两枚鸡蛋分别检验短文、机制长文和推理文的结构，再按文章类型整理其余内容。保留已经清楚的例子、原题、引用和小结。文章结构调整形成新的站点派生稿，记录前后SHA，保护制作稿、媒体、旧冻结及创建/首发身份。

编辑先核对三件事：开头承诺的问题是否由正文回答，每节增加了哪一步解释，结论及必要条件是否能追溯到正文。再请目标读者检验：能否找到要解决的问题，能否解释关键因果，换一个条件后能否作出正确判断。阅读停留和滚动行为可辅助定位卡点，不能单独当作理解程度。

技术验收沿用图文引用/配图检查和正式构建；实际重排后复核旧章锚点、视频回看、图文邻接、手机与桌面的阅读顺序。若加入自检题，检查问题、答案与正文条件一致；若增加交互，保留静态阅读路径。
