空白页背后的四段工作#▶ 从这里看

网址已经输入，页面却还空着。从按下回车到看到商品页，中间需要完成不同层次的工作：找到连接目标、建立连接、请求资源，再把资源处理成画面。TCP三次握手是其中一段，不能替代后面的加密协商、HTTP请求和页面绘制。

本文沿同一个教学示例https://shop.example/products/42展开。主线假设没有可直接使用的缓存和现成连接，使用HTTPS上的HTTP/1.1，并进行常规的证书认证TLS握手。它是一条便于理解的正常路径；实际工作可以重叠，缓存、复用及协议版本也会改变过程。

从网址找到连接目标#▶ 从这里看

网址中的shop.example是主机名，/products/42是请求路径，https指明安全访问的方案。没有显式指定端口时，HTTPS使用默认端口443。

DNS负责从域名查找地址。视频假定得到203.0.113.10，再与端口443一起确定这次连接的目标。端口不是DNS查出来的；域名和路径也不会因为有了IP而失去作用，后面的身份验证与HTTP请求仍然需要它们。

这里的域名和IP都是文档示例，不是一次真实查询。实际解析可能返回多个地址，实际远端也可能是代理或CDN节点，而非直接运行应用代码的源站。

TCP交换并确认双方的起始序号#▶ 从这里看

TCP向应用提供可靠、有序的字节流。双方各自维护发送方向的序号空间；这里的序号指向字节位置，不是“第几个HTTP请求”。TCP也不会替应用保留每次写入的消息边界。

新建连接时，双方需要交换初始序号，并确认对方收到。本例采用不带应用数据的最简三次握手，数字均是教学选择：

次序方向报文中的关键字段这一步完成什么
第一次浏览器 → 服务端SYN, seq=1000告诉对方客户端的初始序号
第二次服务端 → 浏览器SYN+ACK, seq=5000, ack=1001给出服务端初始序号，并确认客户端的SYN
第三次浏览器 → 服务端ACK, seq=1001, ack=5001确认服务端的SYN

ack是期望收到的下一个序号。SYN本身占用一个序号，因此收到序号1000的SYN后，确认号是1001；收到序号5000的SYN后，确认号是5001。第三次这里是纯ACK，不占用序号空间，因此客户端后续第一段数据仍可以从1001开始。

双方进入“已建立”的时刻也不同：客户端收到有效SYN+ACK后，可以进入已建立状态并发送最终ACK；服务端收到这个有效ACK后，才进入已建立状态。图中报文还在途中时，服务端仍在等待确认。

为什么还要第三次

第二次回复之后，客户端收到了服务端的起始序号，但服务端还没有得到对自己SYN的确认。第三次ACK补上了这个确认，使双方都完成“发送自己的序号、确认对方序号”的过程。

RFC 9293还说明，三次握手的重要设计原因是避免历史重复的连接发起造成混淆。服务端仅收到一个SYN，未必能判断它是不是网络中延迟到达的旧报文；让客户端继续确认，可以核对这次连接的序号关系。规范图8展示了旧SYN、错误确认关系及RST的处理。本片不再展开这条支线，也不把三次握手概括成“三次测试收发功能”。

这套过程没有承诺后续永不丢包、永不断线。可靠、有序的服务还依赖TCP在后续传输中的序号、确认、重传等机制；这些机制不属于本片展开范围。

TLS怎样保护连接#▶ 从这里看

TCP解决字节流传输的可靠与有序；它本身不提供网页内容加密。主线的HTTPS连接还需要TLS完成认证、密码参数协商和密钥材料建立，之后用流量密钥保护通信内容及其完整性。

本次选择证书认证的常规新建连接：浏览器核验证书及目标网站身份，双方完成密钥协商。证书中的身份信息和公钥不等于后续直接加密所有网页数据的流量密钥。图中只抽取“身份验证、密钥、受保护的数据”三个职责，不冒充完整的TLS报文序列。

连接恢复、预共享密钥及0-RTT会改变握手细节，所以不能说每一次HTTPS请求都会重新发送证书或重新协商整套连接。QUIC还以另一种方式集成TLS，见后面的版本边界。

看一次具体的HTTP/1.1请求和响应#▶ 从这里看

连接具备传输与安全保护后，HTTP描述要取什么资源。下面是教学请求，展示TLS解密后的HTTP/1.1文本形式：

HTTP · 请求
GET /products/42 HTTP/1.1
Host: shop.example
↵

GET是方法，/products/42是请求目标，HTTP/1.1是版本；Host提供目标主机信息。不能把域名说成只在DNS阶段出现，也不能把上述文本行直接当作HTTP/2或HTTP/3的线上格式。

服务端可以返回成功状态和HTML内容。下面只节选状态行与内容类型字段，省略其他字段和消息定界细节：

HTTP · 响应
HTTP/1.1 200 OK
Content-Type: text/html

200表示请求成功；Content-Type: text/html说明返回表示是HTML。正文才包含页面结构，例如商品标题、价格、按钮，以及样式和图片等资源引用。画面中的正文也是片段，不是一份声称可直接发送的完整响应。

收到HTML后，浏览器还在继续工作#▶ 从这里看

浏览器不必等全部资源到齐才开始解析。HTML解析产生DOM；样式规则形成CSSOM，参与计算元素的样式。随后布局确定可见元素的位置和大小，绘制形成像素，必要时还有图层合成。

解析和预加载扫描还会发现样式、图片等资源，触发更多请求。网络下载、解析与渲染可以交叠；页面先出现、图片随后补齐，并不表示前面步骤都要从头再来。首次出现内容也不等于脚本、图片等全部工作已经结束。

哪些步骤可以省去或改变#▶ 从这里看

情况对过程的影响不能据此推断什么
有符合规则的HTTP缓存资源可能直接复用，或通过验证后复用不是所有“已存过”的资源都能直接使用
已有可复用连接后续请求可以省去重新建连不是每张图片都重新握手，也不保证网站只开一条连接
HTTP/2一条连接中可以有多个并发流，交错传输不同流的帧不是把HTTP/1.1文本请求行原样并行发送
HTTP/3使用基于UDP的QUIC，集成TLS1.3，不经过TCP三次握手UDP承载不代表HTTP/3没有可靠传输或加密

因此，三次握手解释的是本例TCP连接如何建立。要让商品页真正出现，还需要安全协商、HTTP交换和浏览器处理；观察“页面慢”，也需要分清等待发生在哪一段，不能只凭空白页就认定是某一个协议出了问题。
