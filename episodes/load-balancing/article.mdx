十点，活动页 shop.example/sale 开抢。你点开它，页面标题和框架都出来了，下面的活动内容却一直转圈，最后提示「请求超时，请重试」。

打开开发者工具看，加载活动内容的那个请求 `sale-items` 一直显示「待处理」：请求发出去了，服务器迟迟不回应。服务器没坏，只是一台接不住这么多人。

> 说明：shop.example 是专门留给示例用的域名[^rfc2606]；203.0.113.10 属于专门写文档用的示例地址段[^rfc5737]；同时访问人数、各台服务器的请求数，以及「每 5 秒检查一次」「5 秒内没回算失败」「连续 2 次」都是示例数据或示例设置，视频里出现的地方都标了「示例数据」「示例设置」。

## 跟着一次打开活动页走一遍

### 1. 一台正常的服务器也会忙不过来 {#one-server}

{/* 配图：网页版「服务器状态」表，只有一行 A｜20｜40｜正常；待处理请求数 40 → 70 → 100，那一格变橙，状态仍是绿色「正常」；表格下依次写「所有请求都到 A」「正在处理的数量有限」「后来的请求继续等待」 */}

十点一到，所有请求都挤到同一台服务器 A。A 一次只能处理这么多（表里「正在处理的请求数」停在 20），后来的请求只能等着，「待处理请求数」从 40 涨到 100。A 的状态一直是「正常」：它没坏，只是忙不过来。

网站先加上两台服务器 B 和 C，三台都装同样的活动页程序，都能处理这个页面。可大家访问的还是同一个网站地址 shop.example，浏览器不会因为多了两台服务器，就自己挑一台。

### 2. 先接收请求，再分给三台 {#distribute}

{/* 配图：原理演示网页。左边浏览器地址栏图标 shop.example，中间「负载均衡器」框（下写 203.0.113.10），右边 A、B、C 三个框；请求光点先到负载均衡器，再分别去 A、B、C；「处理结果」光点从三台回到负载均衡器，再回到浏览器 */}

**负载均衡器**放在这几台服务器前面，替它们接收所有请求，再分给后面的某一台。[^mdn-proxy][^nginx-lb]

网站的地址现在指向负载均衡器。请求先到它这儿，它把这一个转给 A，下一个转给 B，再下一个转给 C。服务器各自处理，结果先回到负载均衡器，再由它发回浏览器。

在开发者工具里看，这次请求的远程地址是 `203.0.113.10`，也就是负载均衡器；后面由哪台服务器处理，浏览器看不到。

视频里配置好以后重新来一轮：同样 120 个新请求，由负载均衡器分给三台，每台各 20 个在处理、20 个在等；很快待处理都降到 0。每台要等的请求都少了，浏览器不用等那么久，活动页终于打开。负载均衡器只分新到的请求，不会把已经在 A 那里等着的请求搬走。

### 3. B 不回应，就先暂停给它新请求 {#health}

{/* 配图：状态表里 B 变红「无响应」，待处理数 0 → 4 → 12；原理页上负载均衡器向三台发蓝色「检查请求」，只有 A、C 回「回复：正常」；状态表计时「检查开始后 0 / 5 / 10 秒」，B 记「第 1 次：未按时回应」「第 2 次：未按时回应」「连续失败 2 次」后整行变灰「不健康·暂停分配」 */}

可这时 B 的程序卡住，不再回应。A 和 C 还在处理，继续分给 B 的请求却只能等着，分到 B 的那部分人又看到活动页一直转圈。

所以负载均衡器会定时给每台发检查请求，看它能否在时限内回复正常，这就叫**健康检查**。[^gcloud-hc]视频里用的是一组常见默认值：每 5 秒检查一次，5 秒内没回算一次失败，连续 2 次失败就判为不健康；不健康以后，持续检查，连续 2 次成功才恢复。[^gcloud-hc]「回复：正常」是示意：以 HTTP 检查为例，实际要求在时限内收到状态码 200。[^gcloud-hc]

B 连续两次都没按时回应，就被标为不健康，负载均衡器暂停给它分配新的请求，新请求只分给 A 和 C，活动页照样打开。暂停的只是新请求：已经在 B 那里的请求不会因此立刻被终止。[^gcloud-hc]

检查并没有停。B 修好后，连续两次都按时回复正常，才恢复分配，又开始处理新请求。

回到开头：同样是十点，同样多的人打开活动页，这次请求分到三台，页面不再一直转圈。

串起来就是：多台服务器一起分担请求，负载均衡器负责分配，再靠健康检查，只分给正常的那几台。

## 视频里没讲的几件事

**怎么挑下一台：轮询和最少连接**：视频里只演示了「这一个给 A，下一个给 B」，没给分法命名。最常见的默认分法是**轮询**，按顺序一台接一台地分；另一种是**最少连接**，把新请求交给当前活动连接最少的那台，适合有的请求处理得特别久的情况。还可以按服务器能力给不同权重。[^nginx-lb]

**单点故障**：只有一台服务器时，它忙不过来或者停了，整个网站都受影响，这种「一处出问题、全体受影响」的位置叫单点故障。多台服务器加健康检查，可以让一台出问题时其余几台继续接新请求。不过负载均衡器自己也是一个入口，实际部署通常也会让它有备份，这里不展开。

**弹性扩展**：视频里是手动「先加上两台」。很多平台能按负载自动增减服务器数量，人多时多开几台，人少时关掉一些，这叫弹性扩展（也叫自动伸缩）。新开的服务器同样要通过健康检查，负载均衡器才开始给它分请求；健康检查本身不会多开服务器。

**和上一期 CDN 怎么分工**：CDN 把图片、脚本、样式这类人人一样、不常变的文件放到你附近的节点；[^mdn-cdn]活动内容这种每次都要服务器现算的请求，还是要到网站自己的服务器，这时由负载均衡器把它分给后面的某一台。两者常常一起用：前面的节点负责「离你近」，后面的负载均衡器负责「多台一起干」。

**限流**：人实在太多、几台服务器都接不住时，网站还可以限流：超过设定的数量就先不处理，直接回一个「稍后再试」，比如 HTTP 状态码 429 Too Many Requests，[^rfc6585]或者让人排进等候页。这样能保住已经在处理的请求，但会有一部分人暂时进不去。

## 想一想

如果三台服务器同时都不健康，再打开活动页，会看到什么？评论区说说。

**参考答案**：负载均衡器找不到能分配的服务器，活动内容拿不到。以 Google Cloud 的负载均衡器为例：大多数应用负载均衡器会直接返回 HTTP 状态码 503，传统（Classic）应用负载均衡器返回 502；有的类型会直接断开新连接，还有的类型会把流量分回不健康的服务器作为最后手段。[^gcloud-hc-state]所以多半看到的是一个错误页，或者页面脚本显示的「请求失败，请重试」，而不是一直转圈。

## 参考资料

[^mdn-proxy]: [MDN：Proxy servers and tunneling](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Proxy_servers_and_tunneling)，Reverse proxies 小节：放在网站服务器前面接收请求，用途之一是把负担分到多台服务器（Load balancing）。

[^nginx-lb]: [nginx：Using nginx as HTTP load balancer](https://nginx.org/en/docs/http/load_balancing.html)，多台运行同样程序的服务器由前方分发请求；默认轮询（round-robin），另有最少连接（least_conn）、按地址哈希和权重；Health checks 小节说明失败的服务器会被暂时避开。

[^gcloud-hc]: [Google Cloud：Health checks overview](https://docs.cloud.google.com/load-balancing/docs/health-check-concepts)，How health checks work 与 Health state：检查间隔、超时默认都是 5 秒，健康与不健康阈值默认都是连续 2 次；HTTP 检查要求在超时前收到 200；不健康的后端不再接收新连接，已有连接不会立刻终止。2026-10-21 访问。

[^gcloud-hc-state]: [Google Cloud：Health checks overview § Health state](https://docs.cloud.google.com/load-balancing/docs/health-check-concepts#health_state)，全部后端不健康时的行为按负载均衡器类型不同：Classic 应用负载均衡器返回 502，全局/区域外部与内部应用负载均衡器返回 503，代理网络负载均衡器终止新的 TCP 连接，部分直通网络负载均衡器作为最后手段把流量分给不健康的后端。2026-10-21 访问。

[^mdn-cdn]: [MDN：CDN](https://developer.mozilla.org/en-US/docs/Glossary/CDN)，CDN 由分布在各地的服务器组成，就近提供内容。

[^rfc6585]: [RFC 6585：Additional HTTP Status Codes §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)，429 Too Many Requests：用户在一定时间内发出的请求太多。

[^rfc2606]: [RFC 2606：Reserved Top Level DNS Names §2](https://www.rfc-editor.org/rfc/rfc2606.html#section-2)，.example 留作示例用。

[^rfc5737]: [RFC 5737：IPv4 Address Blocks Reserved for Documentation §3](https://www.rfc-editor.org/rfc/rfc5737.html#section-3)，203.0.113.0/24 留作文档示例。
