## AI说要查，订单为何没动 {#hook}

你在退款咨询里问：“帮我查一下，这单签收几天了？”助手已经准备查询订单8124，订单系统却还没有收到查询。**此时只是停在调用请求刚生成的一刻**，不表示系统故障。谁把这项请求变成真正的查询？

本期只跟踪一个自定义只读函数：查询示例订单的签收天数。模型提出工具调用请求，咨询应用的程序检查并执行，再把结果交回模型，最后在对话里回答。上一期[A01](../agent-intro/)讲结果怎样改变下一步；这一期放大其中一次工具调用，不加入退款政策或真正的退款操作。

订单8124和签收3天都是合成教学数据。配套示例确实启动并查询了本机HTTP测试服务；模型的调用请求与最终答复使用固定fixture，没有请求真实模型、真实订单系统，也没有执行退款。动画解释该示例的机制，不能当作真实服务录像。

## 把请求变成真正查询 {#execute}

先回到这次查询的开始。咨询应用把用户问题与工具说明一起交给模型。工具说明告诉模型“可以查询订单”以及“需要订单号”，不是把订单内容预先交给模型，也不授予读取任意订单的权限。官方Function calling文档将自定义函数调用分成提供工具、取得调用请求、应用执行、回传结果和继续请求几个环节。[^functions]

模型返回的请求可以用这三个字段理解：

| 字段 | 本例 | 含义 |
|---|---|---|
| `name` | `get_order` | 想使用哪个工具 |
| `arguments` | `{"order_id":"8124"}` | 要交给工具的参数；Responses中是JSON字符串 |
| `call_id` | `call_demo_01` | 标识这次调用，回传结果时用它关联 |

这张请求里没有签收天数。它表达“请查询这笔订单”，不能证明查询已经发生。应用不能把任意模型输出直接当成可执行命令，而是按照自己的工具映射与校验规则分发；本例核对工具名、参数格式及当前用户对这笔订单的读取权限。工具可见性或严格参数结构，都不能替代业务授权。[^authorization]

当前用户A有读取权限，应用才向本地订单测试服务发出`GET /orders/8124`。服务查到示例记录，返回`{"order_id":"8124","signed_days":3,"usage":null}`；`usage`表示使用情况未知，本期只取签收天数。返回先到应用程序，再以`function_call_output`及同一个`call_id`交回模型；模型拿到资料之后，才形成“这笔订单已签收3天”的用户答复。[^functions]

下面是本地示例准备的回传项，尚未向真实模型发送。应用用`ok`表示查询成功，`data`保存订单资料：

```json
{
  "type": "function_call_output",
  "call_id": "call_demo_01",
  "output": "{\"ok\":true,\"data\":{\"order_id\":\"8124\",\"signed_days\":3,\"usage\":null}}"
}
```

本例只采用Responses API自定义function的字段，SDK参考版本与固定源码见本期研究记录。没有把Chat Completions的`tool_call_id`等字段混入这个结构。实际接入时还应按接口要求保留必要的会话输出；返回结果之后也可能出现下一次调用，本期只讲一次查询的交接。

## 没通过检查会怎样 {#deny}

再开一个独立演示：用户B、新会话，没有订单8124的读取权限。上一次的订单资料不会进入这次会话，计数也从零开始。

即使仍收到同样的查询工具名和订单号，应用也在权限检查时拒绝。**程序没有向订单系统发起查询，测试服务收到的本次HTTP请求为零。**失败结果由应用生成并交回模型，不是订单服务返回的“订单不存在”，更没有新的签收天数。[^authorization]

示例输出中的`application_status: 403`是应用内部的拒绝状态；它不代表测试服务真的收到请求并返回了HTTP403。本次根本没有向该服务发请求。区分这两件事，才能从日志判断拦截发生在哪一层。

配套示例的最终助手答复也是固定fixture：提示当前用户没有读取权限，未查询订单。这个设置用于检查数据交接；不能据此宣称任意真实模型都一定会正确拒绝。真实应用仍须检查最终答复与执行结果是否一致，不能把生成的订单状态冒充查询事实。

在仓库运行示例：

```sh
python3 episodes-codex/agent-tool-execution/demo/tool_demo.py --out /tmp/agent-tool-execution-results.json
```

正常分支实际查询一次并返回签收3天；无权限分支实际查询零次、没有订单资料。工具执行入口、调用标识和事件顺序保存在同目录`verified-results.json`，说明及复跑方式见`demo/README.md`。这些是本地合成示例的执行证据，不是生产系统的成功率或性能测量。

## 怎样确认真的执行 {#recap}

回到开头，模型已经提出要查，只说明调用请求已经生成。在这个咨询应用里，**程序检查通过并实际发出查询之后，才会有对应执行记录和订单返回值**；应用把结果交回模型，对话才有查询依据。

排查时分别看三个位置：模型返回的调用请求、应用的检查与执行事件、工具实际返回的结果。助手自然语言里的“正在查”或“已经完成”，都不能单独证明外部操作发生。

本片讲的是自己实现的只读function工具。托管搜索等工具可能由平台执行，本地运行时工具也有不同执行宿主；“模型提出请求”与“运行环境实际执行”仍是需要区分的职责，不能把本例扩大成所有工具都由开发者电脑运行。[^hosted]
