## 为什么先排除不存在的查询 {#goal}

一个商品目录当前只收录编号101和205。应用查001时，数据库仍要完成一次查询，最后才返回未收录。能否先用一份很小的标记，排除一部分肯定没有的编号？

这里的目标只是判断**某个编号是否属于已收录集合**，不是读取商品名称、价格或库存。即使过滤器认为可能存在，实际商品内容仍由真实目录返回。Redis官方文档将这类结构用于紧凑的成员查询；Cassandra也利用它排除不含目标分区的SSTable文件，减少无用检查。[^redis][^cassandra]

先准备16个只能保存0或1的格子，开始全为0。这是一份**位数组**：

- **下标**是格子的位置，本例从0到15，写在格子外。
- **位值**是格子里的0或1，写在格子内。
- 一个0不是在说某个同号商品不存在，它只表示这个位置尚未置位。

16位、三路计算和下面四个编号都是可复算的教学样例，不是Redis内部参数，也不用于估算线上误判率。

## 同一编号怎样留下标记 {#write}

我们用固定的计算规则，把每个编号映射到三个下标。这个过程称为**哈希**。规则、编码和参数相同时，同一编号每次都落在相同位置；不同编号可能共享位置，不能把哈希理解成一定唯一的标识。

画面上的101、205、001、067，在程序里分别对应字符串`sku101`、`sku205`、`sku001`、`sku067`。教学规则是：分别用seed 0、1、2，计算UTF-8字符串`seed:key`的SHA-256，取摘要前8字节作为big-endian非负整数，再对16取余。

| 身份 | 程序输入 | 三个位置 | 是否先加入目录与过滤器 |
|---|---|---|---|
| 101 | `sku101` | 3、14、15 | 是 |
| 205 | `sku205` | 0、3、12 | 是 |
| 001 | `sku001` | 12、2、15 | 初始否 |
| 067 | `sku067` | 14、0、15 | 否 |

插入101时，只把3、14、15三个位置置为1；插入205时，把0、3、12置为1。3号位已经是1，就仍然保留1，**不会累加成2**。最终为1的位置是0、3、12、14、15，其余仍为0。

这种让多个元素共享紧凑标记的结构，就是这里讲的**布隆过滤器**。Guava的官方源码将插入描述为设置选中的位，将查询描述为检查这些位是否全部置位。实际库也可能从少量哈希结果派生多个位置；本例的三路SHA计算只是教学实现。[^guava]

## 零与一为什么给出不同结论 {#query}

### 001：遇到一个0，就可以停止

查询001，仍用原来的规则得到12、2、15：

1. 12号位是1，暂时还不能判断。
2. 2号位是0，立即返回可以排除。
3. 15号位不必继续读；**不需要等到三个位全为0**。

原因来自插入过程本身：如果某编号已经正确加入过，其对应位置就都被设成了1。规则不变、这些标记没有被错误清除时，查询同一编号不会遇到0。因此在这个维护前提下，遇到0能确定它没有被加入。

已加入的101对应3、14、15，查询时三个位置确实全为1。但这份结果仍然只表示可能存在，过滤器没有取出商品记录。[^redis][^guava]

### 067：全部为1，也可能没加入过

067从未加入，却映射到14、0、15。这三个位恰好都为1：14和15是101留下的，0是205留下的。它们共同制造了一个**假阳性**：过滤器放行了一个实际不在集合中的编号。

这也说明为什么不能把过滤器的阳性当作业务命中：**它只决定是否继续查，真实查询才决定最终返回什么。**在本片路径中，一次假阳性多放行了一次查库，不会凭空造出一条商品记录。

## 省下查询需要什么条件 {#boundary}

### 容量与误判率要一起规划

固定这么多位，加入更多元素后，置为1的位置通常越来越多，未加入编号也更容易碰到全1。实际使用要按预计元素数和可接受的误判率规划空间；更低的目标误判率通常需要更多空间。Redis文档还说明其实现可增加子过滤器，不能把所有产品都理解成单个永不变化的16位数组。[^redis][^cassandra]

假阳性概率说的是：**对实际未加入的查询，过滤器误报可能存在的概率**。它不是所有阳性回答中有多少错误，后者还受查询中真实存在比例的影响。本例只构造了一次可以复算的误判，没有测生产误判率，也不据此声称能节省某个固定比例的数据库请求。

### 普通位数组不能按元素直接清零

如果删除101时，把它的3、14、15全部清成0，仍在目录中的205查询0、3、12时，就会在3号位遇到0，被错误排除。原因是3号位同时被205使用，而普通位数组没有保存每个1的所有者。

这是一段**错误操作反例**，不是基础过滤器支持的删除接口。需要删除能力时，应选择有相应维护机制的结构或重建策略，不能直接把单元素的哈希位置清零。

### 新数据必须反映到摘要中

再看一个独立维护场景：001后来已经加入真实目录，但过滤器还停留在旧状态，2号位仍为0。这时过滤器会错拦真实数据，原来的排除结论已不再安全。

正确把`sku001`加入摘要后，12、2、15都为1，实际新置位的是2号；随后001才会继续到真实目录确认。本片只说明维护前提，不展开分布式写入与切换协议。**只有相关数据已正确反映在这份摘要中，才可以依赖阴性做排除。**

### 可运行的同源教学示例

下面代码使用Python标准库，可直接运行：先写入两条编号，再检查四个编号，最后演示错误清零和新增数据未同步的影响。输出每行依次为编号、三个位置、过滤器是否认为可能存在、真实目录是否收录。

它只是固定16位演示，不含生产库的容量策略、并发控制、持久化或版本兼容保证。进阶读者可查看[完整示例源码](https://github.com/linhongcun/video-studio/blob/main/episodes-codex/bloom-filter/article-demo.py)。

```python
from hashlib import sha256


def positions(key):
    return [
        int.from_bytes(sha256(f"{seed}:{key}".encode("utf-8")).digest()[:8], "big") % 16
        for seed in range(3)
    ]


bits = [0] * 16


def add(key):
    for index in positions(key):
        bits[index] = 1


def maybe_contains(key):
    for index in positions(key):
        if bits[index] == 0:
            return False
    return True


catalog = {"sku101", "sku205"}
for key in ["sku101", "sku205"]:
    add(key)

for key in ["sku101", "sku205", "sku001", "sku067"]:
    print(key, positions(key), maybe_contains(key), key in catalog)

assert not maybe_contains("sku001")  # 遇到2号位的0，可排除
assert maybe_contains("sku067") and "sku067" not in catalog  # 假阳性

# 错误删除反例：不能把某个编号的位直接清零。
saved_bits = bits.copy()
catalog.remove("sku101")
for index in positions("sku101"):
    bits[index] = 0
assert "sku205" in catalog and not maybe_contains("sku205")  # 误清共享位

# 恢复原状态，演示另一个维护场景：新增真实记录后也要更新摘要。
bits[:] = saved_bits
catalog = {"sku101", "sku205", "sku001"}
assert "sku001" in catalog and not maybe_contains("sku001")  # 尚未同步，不能信任排除
add("sku001")
assert maybe_contains("sku001")  # 现在可以继续去真实目录确认
```
