老板刚在后台把价格改低，刷新页面，怎么还是旧价？这一期讲**缓存和数据库一致性**：页面上的价格多半读的是缓存里另存的一份，改价要动数据库和缓存两个地方，两处没法在同一瞬间一起变，中间的空隙就会让人看到旧值。

> 说明：本文资料核查于 2026-10-16。Redis 以 8.x 官方当前文档为准（核查时最新正式版 8.10.2，2026-09-17 发布），MySQL 以 MySQL 8.0 参考手册为准。服务端缓存那期已经讲过「先改数据库、再删缓存」以及先删缓存的竞态；本期展开并发回填、删除失败和主从延迟。官方当前文档没有发布日期，标「官方当前文档（访问于 2026-10-16）」；2020 年以前的资料标 **仅参考**。没有来源的数字一律不写。

## 1. 为什么会不一致

- 数据存了两份：数据库是唯一真相，缓存只是副本。比喻里，仓库的价目账本是数据库，备菜台上的价签是缓存。
- 改价要动两处，而这两步不在同一个事务里：Redis 和 MySQL 是两个独立系统，没法在一个本地事务里一起提交（分布式事务那期讲过这个难处）。
- 只要第一步做完、第二步还没做，就有人可能读到旧值；读和写同时发生时，读的人还可能把旧值重新塞回缓存。
- 微软架构中心明确写到：Cache-Aside 模式**不保证**数据存储和缓存之间的一致性，写入到下一次读取之间，读者可能没命中，也可能短暂看到旧数据[^S1]。

下面记号：价格旧值 99、新值 79（示例，不是数据）。读请求都按 Cache-Aside 读：先查缓存，没命中就查库，再写回缓存[^S1]。

## 2. 直接改缓存行不行（更新缓存）

先改库，再把新值写进缓存。两个写请求并发时会乱序：

| 时刻 | 写 A（改成 79） | 写 B（改成 69） |
|---|---|---|
| t1 | 库 = 79 | |
| t2 | | 库 = 69 |
| t3 | | 缓存 = 69 |
| t4 | 缓存 = 79（A 慢了一步，后到） | |
| 结果 | 库 69，缓存 79，一直错到下次修改或过期 | |

另一个代价：没人读的冷门数据也被写进缓存，白占空间[^S2]。所以更常用的是**删缓存**（撤盘）：

- 删除不会出现「旧值盖新值」，删两次、删晚了结果都是「没有」；
- 只有真有人读才重新放进缓存（懒加载）[^S2]；
- 缓存值如果要拼装计算，删掉比每次写都重算省事；
- 代价是删掉后下一次读会没命中、多查一次库[^S2]。

说明：Write-Through（写库时同步更新缓存）本身是合法方案[^S2]，这里只说在应用自己维护两份数据时，并发写会乱序。

## 3. 先删缓存，还是先改库

### 3.1 先删缓存，再改库

| 时刻 | 写请求 | 读请求 |
|---|---|---|
| t1 | 删缓存 | |
| t2 | | 查缓存，没命中 |
| t3 | | 查库，读到旧值 99 |
| t4 | 库 = 79 | |
| t5 | | 把 99 写回缓存 |
| 结果 | 库 79，缓存 99 | |

微软文档明确建议先更新数据存储、再删缓存，并指出先删会留下这段空隙[^S1]。经验上写库往往比读库慢（要加锁、写日志），读请求有时间插进来——这是经验说法，没有来源给出数字。

### 3.2 先改库，再删缓存（标准写法）

正常情况下，改库后删缓存，下一次读没命中，从库里读到新值补进缓存。它也会出错，但很少。出错的事件顺序是：

**没命中 → 读到旧值 → 新值提交 → 删缓存 → 旧值回填**

| 时刻 | 读请求 | 写请求 |
|---|---|---|
| t1 | 查缓存，没命中（过期或被淘汰） | |
| t2 | 查库，读到旧值 99（写请求可能还没开始，也可能已开始但未提交：InnoDB 一致性读看不到未提交的改动） | |
| t3 | | 新值 79 提交 |
| t4 | | 删缓存（本来就空） |
| t5 | 把 99 回填进缓存 | |
| 结果 | 缓存 99，直到下次删除或过期 | |

关键只有一点：**旧值回填晚于删除**。回填一般紧跟读库之后，删除要等提交之后，所以这种顺序概率低，但不为零。

## 4. 撤不干净怎么办

### 4.1 延迟双删
做法：先删缓存 → 更新库 → 等一小会儿 → 再删一次。第二次删除用来清掉竞态里被读请求塞回去的旧值，也能清掉主从延迟带回的旧值。

- **等多久**：要大于「一次读库 + 写回缓存」的耗时；如果读走从库，还要大于主从延迟。没有权威的通用数字，请按自己系统实测的读耗时和主从延迟来定。
- **局限**：这是中文社区常见的经验做法，本文引用的官方资料里没有直接命名它；它只降低概率，不是保证。等待期间仍可能读到旧值，第二次删除本身也可能失败，所以仍需要 4.2 的重试。

### 4.2 删除失败：消息队列重试
删缓存失败 → 把要删的 key 发进消息队列 → 消费者反复删，直到成功；超过重试次数进入死信队列，人工处理[^S9]。缺点是业务代码要自己发消息。重试间隔等参数以所用消息队列的默认值和配置为准，本文不写具体数字。

### 4.3 订阅变更日志（binlog）
MySQL 8.0 把每个事务的数据改动写进二进制日志 binlog，8.0 默认开启[^S6]。Canal 这类工具伪装成 MySQL 从库读取 binlog[^S8]，看到「价格变了」就去删缓存，失败再丢进消息队列重试。

- 好处：**业务代码不用管删缓存**，也不容易漏删。
- 仍要注意：这条路**仍然需要重试**（删除照样可能失败），也**仍可能有旧值回填**（3.2 和第 5 节的竞态不会因此消失）。
- 版本：canal 最新正式版 canal-1.1.8（2025-01-16）[^S8]。

## 5. 主从延迟叠在一起

写走主库、读走从库时（主从复制那期讲过读写分离）：

| 时刻 | 写请求 | 读请求 |
|---|---|---|
| t1 | 主库 = 79 | |
| t2 | 删缓存 | |
| t3 | | 没命中，去从库读；从库还没同步，读到 99 |
| t4 | | 99 写回缓存 |
| t5 | 从库收到 79 | |
| 结果 | 缓存 99，即使写请求顺序完全正确 | |

对策：

1. 补缓存时读主库，或者刚写过的 key 一段时间内读主库（写完读主库）；
2. 延迟双删的等待时间要大于主从延迟。从库落后多少可以看 `SHOW REPLICA STATUS` 的 `Seconds_Behind_Source`（MySQL 8.0.22 起的名称），但手册也提醒这个值有时不准[^S7]；
3. 订阅**从库**的 binlog，等从库收到这条改动再删，比订阅主库更不容易被从库旧值回填（binlog 在提交完成前写入，仍可能有很短的空隙，所以重试和过期时间照样要有；需要从库开启 `log_replica_updates`，MySQL 8.0.26 起用这个名称，8.0 默认开启）[^S6]。

比喻里的「分仓库」就是从库，对应主从复制那期的「转播电视」：只抄不改，可能慢半拍。Meta 披露的一次真实缓存不一致问题，也涉及数据库复制和跨地域通信[^S3]。

## 6. 兜底：过期时间（TTL）

- 每个缓存都设过期时间，时间到自动删除[^S4]。比喻里是计时牌：**到点就撤**，只看时间，不看价钱有没有变。
- 计时牌保证这一盘旧菜不会永远摆着。⚠ 它不是「最多错多久」的承诺：过期后如果又从落后的从库回填，旧值可能再上台一轮。
- 取舍：TTL 太短，没命中多、数据库压力大；太长，旧数据留得久[^S1]。
- Redis 版本细节：用 `SET` 覆盖一个 key 会清掉它原来的 TTL[^S4]，所以写回缓存时要用带过期时间的写法（如 `SET key value EX 秒数`），否则这份缓存永不过期，安全网就漏了。Redis 2.6 起过期误差在 0–1 毫秒[^S4]。删除用 `DEL`[^S5]。

## 7. 强一致很贵，最终一致是常态

- 想让缓存和数据库任何时刻都一样，得把「改库 + 改缓存」放进一次分布式事务或加锁串行，读写都会变慢，缓存的意义就打了折扣。比喻里就是「改价时全店停单」。
- 常见做法是**最终一致**：允许短时间旧，保证最后一定变新（删除 + 重试 + 过期时间）。Cache-Aside 本身不保证一致[^S1]。
- **靠谱的系统结账按仓库账本算**：钱、库存扣减这类操作以数据库为准，下单时按数据库里的价格和库存算，缓存只负责展示。这是通用设计原则，没有单一权威出处，也不是所有网站都保证。
