# 第二期方案：《HTTPS 为什么安全？》

目标：零基础观众看完能说清楚——HTTP 明文有什么风险，HTTPS 靠哪三件事解决（加密、身份认证、完整性），以及 TLS 握手大致怎么完成。定位科普，不使用求职向表述。

## 贯穿意象
「寄一封不想被偷看的信」：明信片（HTTP）→ 上锁的信箱（加密）→ 邮局盖章的身份证明（证书）→ 防拆封条（完整性）。锁与钥匙动画贯穿全片。

## 主线（6 章）
1. 明文的风险：HTTP 像明信片，路上的人能偷看（窃听）、偷改（篡改）、冒充（伪装）
2. 对称加密：一把钥匙加解密，快；难题是钥匙怎么安全交给对方
3. 非对称加密：公钥上锁、私钥开锁，解决送钥匙问题，但慢；所以 HTTPS 混合使用——用非对称方式协商出对称会话密钥，再用对称加密传数据
4. 证书与 CA：公钥可能被中间人调包；CA 签发证书证明「这个公钥属于这个网站」；浏览器沿证书链校验到内置根证书；地址栏锁图标的含义
5. TLS 握手（以 TLS 1.3 为主）：ClientHello（支持的算法 + 密钥交换参数）→ ServerHello + 证书 + 签名 → 双方用 ECDHE 算出同一会话密钥 → 加密通信；一句带过 TLS 1.2 需两次往返、1.3 为一次
6. 完整性与收尾：消息认证（AEAD）让篡改会被发现；回到明信片对比；常见误区：HTTPS 不等于网站可信、不保护你设备上的数据

## 准确性要求
- 以 RFC 8446（TLS 1.3）、MDN、Let's Encrypt 文档为准，标注来源与日期；2020 年前资料标「仅参考」
- 避免旧说法：不要讲「客户端用公钥加密会话密钥」（RSA 密钥交换，TLS 1.3 已移除），以 ECDHE 为主；可在图文里注明历史做法
- 不讲 SSL 为现行协议；SSL 已废弃，统称 TLS
