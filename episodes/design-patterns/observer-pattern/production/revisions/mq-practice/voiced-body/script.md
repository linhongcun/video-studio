# 《观察者模式：订单变了，谁该收到通知？》

2026-10-25（北京时间），设计模式D02。按用户最新反馈改为实战导向：保留订单17、摘要和变化记录的产品需求，用一镜简述观察者原理，主要篇幅讲跨服务MQ发布订阅、独立消费、离线积压、恢复重投与幂等，再说明一致性和范围选择。

- 本次新指令取代此前完整演示订阅/取消/发货的内容重心。01为产品入口；02为同进程原理；03起明确切到跨服务教学示例。内部服务架构是本项目设计，不推断真实商家系统。
- MQ不等同于所有观察者实现；跨服务业务通知经常借助消息中间件，同进程仍常用事件监听/框架事件。所有统计式市场占比判断均不进入视频。
- 跨服务具体示例采用RabbitMQ的交换机、各订阅方独立队列、手动消费确认。两业务不能竞争同一队列；持久队列/持久消息/发布确认与重试策略需要配置，不承诺绝对不丢、恰好一次或强一致。
- 06明确回放到尚未消费的故障前提；07承接恢复，处理后确认丢失，检测断连后才重投；幂等要求去重记录与业务效果原子提交，不是先查询编号再独立写入。08是另一条一致性边界示意，不能把失败支线连成同事件依次经历所有故障。
- 每镜两句旁白；正式句首cue为02“观察者模式”、03第二句“消息队列”、07第二句“幂等”。正文无代码教学，片尾仅5秒静默Java原理节选卡；完整可运行示例留图文。
- 深色干净canvas；真实产品功能教学重建可显示界面，内部机制不用浏览器壳。无装饰进度条，无语速加速。

### 05 independent-consume

frame：canvas
章节：各自消费，处理成功后确认
画面：承接04两队列已有同一事件。摘要服务取自己一份、显示已付款、返回手动确认；记录服务取自己一份、追加事实、确认。确认箭头与事件方向相反，未处理前不能先确认。再虚线提示新增订阅方及事件约定不变的前提，不暗示无需配置或永远无需修改生产者。
旁白：两个服务分别消费自己队列里的事件，更新摘要或追加记录，处理成功后再确认。以后增加新的订阅方，订单服务仍按原约定发布事件，不必调用对方。
屏幕文字：分别消费；处理成功→确认；事件约定不变时可增加订阅方

### 07 recover-idempotent

frame：canvas
章节：故障后积压、恢复与幂等
画面：服务恢复，消费记录队列中的事件e17并追加唯一记录；该次确认丢失，以可见断连并检测后重新入队再投递，不能画普通计时器自动重投。第二次相同e17经原子去重/业务事务逻辑跳过业务写入并确认，记录仍一条。编号仅教学示例，幂等正式术语按第二句句首起音入场。
旁白：服务恢复后，再消费积压的事件；处理成功后，如果确认丢失，事件可能再次送达。幂等，就是让同一事件只产生一次业务效果，本例按事件编号去重。
屏幕文字：恢复消费；同一事件e17；确认丢失/断连后重投；幂等 · 业务效果一次
