# 《观察者模式：订单变了，谁该收到通知？》

2026-10-25（北京时间），设计模式D02，制作issue #164。语言无关的设计思想定稿；导演及独立概念审读已通过，后续配音与画面仍需各自验证。自然配音和动作停留决定时长，不靠加速。

- 面向未学过观察者模式的观众，无特定语言、函数、参数或类语法前置。视频不出现代码，具体实现仅作文章可选拓展。
- 唯一贯穿示例：同一程序内的订单17，从待付款变已付款，再变已发货。来源每次先更新状态，再通知当前名单。示例订单号与状态不是外部服务的实际执行。
- 两个接收者：订单摘要显示最后收到的状态；变化记录按收到顺序新增变更事实。变化记录是教学示例的接收者，不是消息队列、可靠投递日志或业务统计。
- 第一次变更，两者已订阅并依次收到已付款；关闭摘要时取消订阅，第二次只有变化记录收到已发货。摘要保留的已付款必须标“最后收到/已停止接收”，不能伪装成当前状态。
- 主线回答三问：为什么避免来源点名响应细节；订阅集合和共同通知约定怎样分离变化与响应；什么时候收益值得维护订阅关系的成本。
- 共同约定包含订单号与新状态；消息交代发生的事实，各接收者决定响应。来源仍持有订阅关系并依赖约定，不是完全解耦。
- 同步依次通知只属于本例。模式本身不统一保证顺序、异步、错误隔离、崩溃恢复、跨服务可靠投递或恰好一次。
- 首现术语cue均使用真实句首：03第二句“订阅”、04第一句“观察者模式”、08第二句“取消订阅”。03、05、08、10各章先口头承接并交代接下来方向，再引入动作。深色干净canvas，稳定对象位置，逐步揭示，无比喻、假应用外壳、密集类图或装饰进度条。
- 来源映射与边界见下表；实际访问记录、正文依据和版本见`research.md`，示例行为由`demo/verify.py`与`demo/verified-results.json`支撑。实现运行只能证明本例行为，不代替设计思想审查。

### 01 order-change

frame：canvas
章节：订单变了，谁要跟着响应
画面：首帧是明确标示例的订单17、待付款状态，以及旁边两个实际功能：订单摘要、变化记录。标题“订单变了，谁要跟着响应？”在2秒内可见。展示付款需求所带来的两项响应，用待执行方向说明目标，不提前将两模块执行完成。
旁白：商家处理十七号订单，付款后，摘要要显示已付款，变化记录也要记下一条。订单处理要认识每一个接收消息的模块吗？
屏幕文字：示例订单17；待付款；订单摘要；变化记录

### 02 direct-dependencies

frame：canvas
章节：订单变了，谁要跟着响应
画面：展开订单处理边界，内部逐一出现“通知摘要”“通知记录”两项具体安排。两条有向线连向对应功能，新增接收方的空位使该安排区域被框选；不新增第三个真实接收者，不把简单直接方案画成故障。
旁白：最直接的安排，是让订单处理点名通知摘要和记录。每多一个接收方，都要回来调整这份安排，接收需求和订单处理就缠在了一起。
屏幕文字：订单处理；点名通知摘要；点名通知记录；接收方变化→调整通知安排

### 03 register-interest

frame：canvas
章节：先登记，再按共同约定通知
画面：先保留原具体依赖，口头过渡后才让两接收者依次向订单侧登记。订单旁形成“当前接收者”名单，先摘要一行、再变化记录一行。箭头方向是登记流向来源；尚未发生订单状态更新，不出现通知令牌。
旁白：接下来，把谁需要消息，从订单怎样变化里分开。订阅，就是摘要和变化记录先登记接收意愿，订单一侧保留当前接收者的名单。
屏幕文字：订阅；当前接收者；摘要；变化记录

### 04 common-notification

frame：canvas
章节：先登记，再按共同约定通知
画面：句首“观察者模式”按声学起音出现主标签并完整显示至少63帧。保留来源与当前接收者，旁边只展开共同通知的两项内容“订单号”“新状态”；用两个不同响应落点说明摘要负责显示、记录负责留痕。此时是关系说明，不把示意消息误当一次已执行的更新。
旁白：观察者模式，让关心变化的接收者先订阅，来源变化时通知它们，这些接收者就是观察者。这里约定通知包含订单号和新状态，收到后怎样响应，由各观察者负责。
屏幕文字：观察者模式；共同约定：订单号＋新状态；各自负责响应

### 05 change-before-notify

frame：canvas
章节：跟着一次变化走一遍
画面：第一句留出关系总览，第二句先让订单17本体从待付款变为已付款并稳定显示，再生成本次“17·已付款”通知，沿名单中的第一条路径前进。接收者尚未收到前不能先更新；发出的是状态事实，不是要求执行付款的指令。
旁白：订阅关系建立后，跟着这次付款走一遍。订单先从待付款改成已付款，再把十七号、已付款这条消息，发给名单里的接收者。
屏幕文字：订单17：待付款→已付款；先更新状态；再通知当前接收者

### 06 each-reacts

frame：canvas
章节：跟着一次变化走一遍
画面：连续完成05通知过程：摘要收到后状态才变为已付款；随后沿第二条路径送达变化记录，新增唯一“17·已付款”一行。前一接收者响应完成后才开始后一条，不画同时扇出；已处理通知不重复计入记录。
旁白：摘要收到消息，显示十七号已付款，变化记录收到后，再新增同样的变更事实。本例依次通知，一方处理完，再轮到另一方。
屏幕文字：摘要：17 已付款；变化记录：17 已付款；本例依次通知

### 07 separate-responsibilities

frame：canvas
章节：跟着一次变化走一遍
画面：保留已付款与第一条变化记录，用职责边界依次圈定摘要的显示和记录的新增，再回到来源旁的名单和共同约定。不要给画面叠上另一份名单或将所有连线消除；明确降低的是对响应细节的依赖。
旁白：显示状态和留下记录，是两个接收者自己的工作，订单不用掌握这些细节。它仍要维护接收者名单，并按共同约定通知，双方的联系没有消失。
屏幕文字：订单：状态变化与通知；摘要：显示；变化记录：留痕；仍依赖名单与约定

### 08 unsubscribe-summary

frame：canvas
章节：取消订阅后，再看下一次变化
画面：先保留07结果承接口头转向，再发生关闭摘要动作。摘要向来源取消登记，名单中的摘要行和后续通知路径移除。摘要位置保持，灰显“已停止接收”，旧值标“最后收到：已付款”，不能冒充当前订单状态。变化记录仍留在名单。
旁白：这次两个模块都收到了，接下来关闭摘要，让它退出。取消订阅时，把摘要从名单移除，变化记录继续保留。
屏幕文字：取消订阅；当前接收者：变化记录；摘要已停止接收

### 09 notify-remaining

frame：canvas
章节：取消订阅后，再看下一次变化
画面：来源订单17已付款→已发货，再发送本次“17·已发货”通知，仅沿仍在名单的记录路径移动。记录保留上一行已付款，再新增已发货一行。摘要继续灰显最后收到已付款/已停止接收，无令牌、无状态更新；不得画成同一订单重新付款或情景重置。
旁白：同一订单接着变为已发货，订单只通知仍在名单里的变化记录。记录新增已发货，退出的摘要没有再收到这条消息。
屏幕文字：订单17：已发货；变化记录：已付款、已发货；摘要已停止接收

### 10 change-membership

frame：canvas
章节：收益、成本和适用边界
画面：第一句回看同一稳定来源与先两人/后一人的接收关系，第二句显示“共同约定不变”前提，圈定名单的增减和接收者自己的响应区域，订单状态处理保持原锚点。无无限扩张承诺，不声称整个系统从此无需修改。
旁白：两次通知对比后，再看这种分工解决了什么变化。共同约定不变时，本例可以通过订阅调整接收者，而不用把它们各自的响应细节写进订单处理。
屏幕文字：共同约定不变；接收者可以增减；响应细节各自维护

### 11 lifecycle-and-delivery

frame：canvas
章节：收益、成本和适用边界
画面：先重新聚焦退出摘要时清理名单的动作，随后以短边界说明显示同一程序范围。不要演成已经存在消息队列、持久化日志或自动重试，更不能将变化记录中的业务留痕当成可靠投递设施。
旁白：这份名单也有维护成本，不再需要时应及时取消订阅。同一程序内的通知，不保证程序崩溃后还能补发，可靠投递需要另外设计。
屏幕文字：维护订阅的生命周期；同一程序内；崩溃补发需另外设计

### 12 idea-recap

frame：canvas
章节：收益、成本和适用边界
画面：先给一个稳定接收方的简洁直接路径，再回到本例最终结构：来源订单17已发货、当前名单仅变化记录、历史两条记录、灰显已退出摘要。按“来源变化→通知当前订阅者→各自响应”回收主线，以“IT小村·原创”收尾，不添下期标题或装饰进度条。
旁白：只有一个长期固定的接收方时，直接通知往往更清楚。观察者模式把状态怎样变化，和收到后做什么分开，用可增减的订阅关系，把双方接起来。
屏幕文字：来源变化→通知当前订阅者→各自响应；按需要选择；IT小村 · 原创
