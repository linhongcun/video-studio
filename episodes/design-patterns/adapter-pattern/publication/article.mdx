## 为什么主动包一层 {#why}

商家打开十七号订单的详情，点击“发送发货提醒”。提醒发给`buyer17@shop.example`，正文是“订单17已发货”；页面得到受理编号Q17，显示“已受理·等待回执”。这些都是教学示例，不发送真实消息。

接入外部服务时，我们可以主动先做两件事：

1. **按业务需要定义自己的约定**。发货提醒需要表达的是“提交收件人和正文，拿到受理结果”。业务代码可以用这份清楚的约定，不必照着供应方的字段、参数对象和状态码来写。
2. **把外部接口细节留在接入边界**。供应方以后更改请求格式或回执包装时，优先在这一层调整，让业务流程少跟着变化。

因此，不必等到一次旧接口故障，才考虑包装外部服务。也可以在最初接入时，就主动决定业务自己的使用方式，再把外部能力接到这份约定上。这里的适配器负责真实的接口转换与委托，不只是多加一个名字。[^spring][^acl]

先看接入设计，再回看开头同一次提交；最后比较后来一次格式升级。开发时的改动和运行时的消息分开，不能把升级对照当成又发送了一条提醒。

## 业务约定与适配结构 {#roles}

本例把四个角色对应到刚才的功能：

| 角色 | 对应对象 | 职责 |
|---|---|---|
| 业务方 | `ShipmentReminder` | 按业务需要提交发货提醒 |
| 业务目标约定 | `Notifier` | 提交收件人/正文，返回受理结果 |
| 适配器 | V1的`NotificationAdapter`，升级后的`NotificationAdapterV2` | 履行业务约定，转换请求与返回，委托持有的服务 |
| 外部服务 | `VendorSdk`或升级后的`VendorSdkV2` | 按供应方自己的方式处理请求 |

业务方依赖的是自己的通知约定。适配器履行它，同时持有外部服务对象，把外部用法转换成业务需要的用法。这就是本例的**对象适配器**关系。[^spring][^jdk]

目标约定是契约，不是中间运行模块。它不会接收、排队或转发消息；具体调用接到的是履行这份约定的适配器。业务规则仍留在业务方，供应方协议细节由适配器处理。

去程分两步：业务方按自己的约定提交地址和正文；适配器将它们转换成服务接收的格式，再调用自己持有的服务。输入值不改变，真正提交的能力仍由外部服务执行。

回程也分两步：服务返回自己的排队结果和编号；适配器把它转成业务的已受理和原编号，再交回业务方。页面因此显示“已受理·等待回执”。

| 同一次提交 | 本例实际表达 |
|---|---|
| 业务输入 | 收件人`buyer17@shop.example`，正文“订单17已发货” |
| V1服务请求 | `Payload(target, body)`，两项值原样对应 |
| V1服务回执 | `RawReceipt("QUEUED", "Q17")` |
| 业务得到的结果 | `Submission(ACCEPTED, "Q17")` |

“已排队”是本例模拟回执的含义，不表示教学程序真的运行了后台投递任务。受理不等于送达；这项结果边界和技术异常的完整处理放在下方扩展中复查。

## 把升级影响留在接入边界 {#boundary}

### 一次后来发生的格式升级

假设外部服务推出V2：输入字段改名，回执又多包了一层。这是**开发变更对照**，不是在开头那次请求中热换服务，也不是再给订单17发一条提醒。

| 对照位置 | V1 | V2 |
|---|---|---|
| 输入 | `Payload(target, body)` | `Envelope(destination, content)` |
| 回执外形 | `RawReceipt(status, ticket)` | `ReplyV2(receipt)`，里面才是`ReceiptV2(state, reference)` |
| 服务受理状态 | `QUEUED` | `ENQUEUED` |
| 服务受理编号 | `ticket = Q17` | `receipt.reference = Q17` |
| 业务需要 | 提交收件人/正文，得到受理结果 | 保持同一业务需要 |
| 业务目标约定与使用者 | `Notifier`、`Submission`、`ShipmentReminder` | 复用原有类型和业务调用 |

我们在V2适配器里调整请求和返回转换，再在外部创建、接线处选用V2服务。业务方继续按自己的通知约定提交，不需要自己去拆新的回执包装。

这个变化有实际程序支撑：原[AdapterDemo.java](https://github.com/linhongcun/video-studio/blob/main/episodes-codex/adapter-pattern/demo-java/AdapterDemo.java)及原验证器字节保持；新[AdapterUpgradeDemo.java](https://github.com/linhongcun/video-studio/blob/main/episodes-codex/adapter-pattern/demo-java/AdapterUpgradeDemo.java)复用原来的`Notifier`、`Submission`与`ShipmentReminder`，新增V2接口、适配器与接线。V1/V2各自独立运行验证，业务调用均得到`ACCEPTED/Q17`；两个版本的测试各自独立，不能理解为商家又点了一次发送。[^demo]

这里隔离的是**业务需要与结果含义不变时的外部格式变化**。新增适配器、外部依赖、创建接线和测试仍要维护。如果新服务不再满足业务需要，或者业务目标本身变了，上层也可能需要调整；不能把一次格式升级的局部修改，扩大成所有升级都零影响。

### 防腐作用与适配器的区别

这层有保护业务边界的作用：业务保持自己的规则和用法，外部模型、字段和状态表达留在接入处转换。Microsoft的防腐层说明同样强调，业务一侧保持自身的数据模型，外部调用遵守外部模型，并把保护领域模型作为核心目的。[^acl]

但**适配器不等于完整防腐层**。适配器是一种把已有接口转换成目标约定的设计关系；防腐层是保护业务模型的架构目的，可能包含适配器、外观或更完整的语义转换。本例主要演示通知接口的技术约定与格式隔离，没有展示一整套生产领域模型的语义治理，也没有把业务规则搬到适配器里。

**有一层包装，也不自动等于适配器**。还要看它是否将外部用法转换成目标使用方需要的约定。OpenJDK也存在保持原有InputStream约定的包装；这说明“持有另一个对象并委托”本身不足以判定模式。[^wrapper]

### 扩展：结果与异常也属于约定

目标通知约定只承诺提交并报告受理情况，不承诺送达。V1的`QUEUED`、V2的`ENQUEUED`在本例都只映射为业务`ACCEPTED`，保留同一编号，不能直接改成`DELIVERED`。RFC9110的202也区分接受处理与完成；这里用它核对边界，没有声称教学SDK实现HTTP202。[^http202]

服务明确拒绝时，本例映射为拒绝；技术异常、超时或未知/无效回执用`SendFailure`表示未能确认结果，并保留原异常原因。服务可能已经受理，回包却丢失，因此不能将未知硬当作确定拒绝。本例不自动重试，也不自带去重、撤销或可靠送达能力。新旧示例都验证这些边界，具体行为以接口约定和完整代码为准。[^demo]
