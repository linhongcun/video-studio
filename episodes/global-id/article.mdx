你刚下的单，客服一查，同一个订单号下面竟然还有别人的订单。订单太多，数据库拆成了好几个，每个都自己编号，就撞了。这一期讲全局唯一 ID。

> 说明：本文资料核查于 2026-10-15。旁白主线是雪花式直觉；号段、UUID、MySQL 步长配置等细节只写在这里。Snowflake / Leaf 设计原文多早于 2020，标「仅参考」，机制可讲，位宽与压测数字不进口播。

## 1. 为什么本机自增会撞

上一期把数据拆到多个分片之后，写压力分散了；但各分片若仍用本机自增当订单号，很容易打出同一个值。Azure 架构中心写明：非分片键上的自增字段，不同分片里的两条数据可能被赋成同一个 ID。[^S4]

以 MySQL 8.4 为例：

- `AUTO_INCREMENT` 给新行生成「唯一身份」——作用域是**这一张表、这一台服务器上的序列**，不是跨机全局约定。[^S1]
- InnoDB 每张带自增的表有内存计数器；重启后从数据字典 / redo 恢复；回滚会留下空洞，但仍然只保证本表内不重复。[^S2]
- `auto_increment_increment` / `auto_increment_offset` 本意是循环复制（多源写）时错开序列；会影响该服务器上**所有**自增表，且分片数量一变步长就要改，扩容不灵活。[^S3] 旁白不展开，细节放这里。

结论：每个分片各自从本机序列往上加，互不知道对方发到哪——很容易撞号。这不是 MySQL「坏了」，是自增的作用域本来就在单机。

## 2. 雪花式（旁白主线）

Twitter Snowflake（开源归档，约 2010，**仅参考**）的目标包括：各机不必互相商量再发号（Uncoordinated）、大致按时间有序、尽量紧凑。[^S7] 组成直觉（**位宽数字只写文章、不上画面、旁白不念**）：时间戳部分 + 配置好的机器号 + 同一毫秒内的序号。[^S7]

旁白对应的比喻：时间色带 + 站徽章 + 同瞬流水戳。机器之间多数时候不用排队领号。

时钟往回拨时，原版 `IdWorker` 会拒绝发号（"Clock moved backwards. Refusing to generate id"）——宁可暂停，也不冒险撞号。[^S8] 旁白只保留一句：「宁可先停下来也不打重复条码。」

美团 Leaf 的 Snowflake 模式「算法取自 twitter 开源的 snowflake」；另有号段模式（见下）。[^S9][^S10] Apache ShardingSphere 也内置 `SNOWFLAKE` 主键生成器，说明中间件生态常用同类思路（举例，不做推荐）。[^S13]

## 3. 号段（只放文章）

Leaf 号段模式：服务从 DB 一次取走一段号（`max_id` + `step`），在内存里往下发；双 Buffer 可在一段用完前异步取下一段，短期可容忍 DB 不可用。[^S9][^S10]

开源说明对比：号段「低位趋势增长」「能容忍 MySQL 短时间不可用」；Snowflake「完全分布式，ID 有语义」。[^S9]

代价要诚实：发号仍依赖（或阶段性依赖）中心号段表——不是「完全去中心」，而是「少打几次 DB」。比喻：总务处一次发给每个窗口一整叠空白号牌，窗口自己撕着用。

## 4. UUID / ULID（只放文章）

RFC 9562（2024-05）把 UUID 定为 128 位，不需要中央权威；动机里写明：分布式场景下协调连续数字编号的成本很容易变成负担。[^S5]

- **UUIDv4**：随机 / 伪随机；适合不想暴露创建时间；但非时间序版本数据库索引局部性差（连续插入在 B-tree 里东插西插）。[^S5]
- **UUIDv7**：Unix 毫秒时间在高位 + 随机/计数；规范建议在可能时优先用 v7 代替 v1 / v6；便于按时间排序、改善索引局部性。[^S5]
- **ULID**（社区规范）：128 位；毫秒时间 + 随机；字典序可排序。RFC 9562 动机列表把它列为既有实践之一；若只点名一种「随机全球号」，优先说 UUID，ULID 作对照。[^S11][^S5]

旁白未点名：自己生成、更长；随机版索引更碎——需要时再进口播。

## 5. Redis INCR（旁白一句，细节在此）

`INCR` 原子 +1；键不存在则当 0 再加；限 64 位有符号整数。官方文档主讲 counter / rate limiter，不是「分布式主键最佳实践」专文。[^S6]

全局唯一且连续的前提是所有人找同一套 Redis 计数——简单，但重新引入单点 / 中心瓶颈。持久化与故障切换若丢计数，有重复风险；**无 Redis 官方「用作订单主键」保证**，本文不承诺「绝对安全」。旁白只说：「也可以用 Redis 这种公共计数器，但大家又都挤回一台发号机了。」

## 6. 方案怎么选（对照）

| 方案 | 旁白 | 本文 |
|---|---|---|
| 撞号原因（本机自增） | 必讲 | §1 |
| 雪花式 | 主线，并点名「雪花算法」 | §2（含位宽、epoch、worker 分配等数字） |
| 时钟回拨 | 一句宁停勿撞 | §2 |
| 号段 | 不进旁白 | §3 |
| UUID / ULID | 不进旁白 | §4 |
| Redis INCR | 公共计数器一句 | §5 |
| MySQL increment/offset | 不进旁白 | §1 |

数据库拆开之后，主键也要按「全局不撞」来设计。
