## 两笔订单同一个号 {#hook}

接上期，订单分到多个数据库。两个独立表都可能从相同起点继续编号，各自在本表内正常，却产生相同订单号。本期订单、相对时间、生成器编号均为教学示例，不代表真实事故。

这就是**分布式 ID**要解决的问题：多个节点生成编号时，怎样避免在约定范围内重复。“全局唯一”描述的是唯一性的范围与要求。下面依次看几种生成方式，了解它们怎样取号，以及各自需要付出什么代价。[^current]

## 本表自增为何不够 {#local}

MySQL的AUTO_INCREMENT能为记录自动生成编号，官方示例配合主键约束使用。约束保障的是所在表，独立分片之间不会自动交换“某个号已经被使用”的信息。[^auto][^current]

也可以统一规划不同起点和步长等生成规则，不能把本表自增的局限理解为自增永远不能用于分布式设计。

## UUID：方便生成，主键有代价 {#uuid}

先看随机版本的 UUID，也就是 **UUIDv4**。各节点可以在本地生成，不必每次请求中心发号服务；可靠的随机源与正确实现能让碰撞概率很低。它没有按生成顺序递增的保证。[^uuid]

这个特点会影响数据库写入。在 MySQL 的 InnoDB 引擎中，主键通常就是存放行数据的聚簇索引。直接用随机 UUIDv4 做主键，连续生成的新值可能落到不同的索引叶子页，写入局部性较差；页空间不足时还可能触发分裂，带来额外的维护和读写开销。索引本身仍按主键顺序组织，随机的是新值的插入位置。[^clustered][^physical][^uuid]

按主键顺序插入通常更有利于 InnoDB 写入，表超出缓冲池时尤其值得关注。具体代价仍受表大小、缓存、并发和索引设计影响，本片不提供统一的性能倍数或“一次插入就一定分裂”的结论。[^bulk]

UUID 不只有随机版本。UUIDv7 把时间放在高位，设计上有利于时间排序和索引局部性；它也不是跨机器业务顺序的严格全序。这里对“不递增”的讨论限定于前面介绍的随机 UUIDv4。[^uuid-order]

## Redis：递增取号，切换要防回退 {#redis}

再看 Redis 自增。多个节点向**同一个计数器**执行 `INCR`，通过原子递增集中分配编号；在计数状态正常保留的运行区间内，可以依次取到1001、1002这样的号码。计数器和数字均为教学示例。[^incr]

主从切换有一个常见的坑：Redis 默认异步复制，旧主已经返回给客户端的计数更新，可能还没到达副本。例如，旧主已发出1001、1002，副本却只保存到1000；旧主故障后，这个副本升为新主，再次递增就可能重新发出1001。`INCR` 的原子性保障单次递增，异步复制的丢写窗口仍需要另行处理。[^replication][^sentinel]

一种治理办法是**事先可靠预留号段，切换时放弃旧号段并跳号**。为说明条件，假设在旧主使用1001—1200之前，已通过另一份可靠记录原子地预留到1200；切换时先暂停发号并停止、隔离旧主，再放弃整个旧号段，将下一号推进到1201。即便副本只保留1000，也不回头重用旧号段中的1001、1002。

这里的1200是**事先预留的上界**，不是事故发生后随意挑选的数字。可靠记录必须能承受本次故障，不能和同一个 Redis 计数器一起回退；恢复和重新预留也必须互斥。跳过的范围要覆盖旧主可能已发出的号码，无法确认边界时应暂停核对。单纯“切换后固定加一个数”、只查看已落库的业务记录，或只开启某个持久化选项，都不能直接推出没有重复。号段示例是基于丢写风险推导的发号设计条件，并非 Redis 或 Sentinel 自动提供的保证。[^replication][^persistence][^sentinel]

集中发号还要维护计数器、网络与故障恢复，不能让key被重置、过期或被独立计数器重复使用。接下来看看各生成器可以在本地组合编号的雪花算法。

## 三部分如何区分 {#snowflake}

雪花算法通常将时间、生成器标识与序号安排在不同字段。不同毫秒可由时间区分；同一毫秒中，不同生成器由身份区分，同一生成器的多个请求由序号区分。[^current]

原始Twitter实现把机房号和机器号分开。本片用“生成器的机器编号”概括它们组成的身份字段，不能把两个进程共用一个身份仍当作两个不同生成器。历史原实现仅用于解释原理，不作为当前部署默认配置指南。[^original]

画面的三段带颜色是**字段示意**。真实结果按整数位运算组合，不是直接连接十进制字符串。示例采用10位生成器身份、12位序号，使用以下相对时间生成17位整数：

```js
const id = (4000000000n << 22n) | (7n << 12n) | 0n;
const text = id.toString(); // "16777216000028672"
```

同一相对毫秒、机器编号9得到`16777216000036864`；机器编号7但序号1得到`16777216000028673`。这三者精确不同。字段范围、纪元、身份分配与运行状态仍要由实际系统正确维护。[^implementation]

## 不重复需要前提 {#conditions}

- 活跃生成器不能误用同一身份；重启或复用身份时也应处理先前状态，不能随意从相同时间和序号重新开始。
- 时钟回拨需要依实现拒绝、等待或其他正确策略处理，不能让时间倒退后照常重用相同组合。
- 同一毫秒的序号用尽，要等到下一毫秒等规则处理，而非直接绕回重复发号。原始实现有明确等待与回拨错误分支。[^original]

这些前提不是人工记住一句“用了雪花”就会自动满足。当前实现的worker-id分配与容忍时间差等参数也有明确要求，适用范围应以所用实现为准。[^current][^implementation]

### 大整数与顺序

JavaScript的Number安全整数最大值为`9007199254740991`。本片17位示例超过这个范围，因此全部用BigInt从整数或字符串构造，再以字符串显示，不经Number转换。跨接口传递时也要遵循明确的字符串等序列化约定。[^number]

时间字段常使编号具有一定时间顺序特征，但跨机器的时钟、调度和业务执行顺序不能据此变成严格的全局业务先后；编号也不是秘密或授权凭证。

## 三种差异各管什么 {#recap}

本片想说明的是：本地自增只看到自己，跨分片要统一设计编号范围和生成规则。雪花算法通过时间、生成器身份和序号分工，在前提得到正确维护时，让各处可分别生成不冲突的编号。

这几种方式各有适用的取舍：

| 生成方式 | 主要收益 | 需要承担的代价或前提 |
|---|---|---|
| 随机 UUIDv4 | 节点本地生成，不必逐次向中心取号 | 依赖可靠随机源；值不按生成顺序递增，直接作 InnoDB 主键需考虑随机插入代价 |
| Redis 自增 | 同一计数器原子递增，取号机制直接 | 依赖共同计数源及网络；异步复制下切换可能重号，恢复与跳号需有可靠边界 |
| 雪花算法 | 各生成器按规则独立生成整数，时间字段提供顺序趋势 | 维护生成器身份、时钟与序号状态；不能据此推断严格的全局业务顺序 |
