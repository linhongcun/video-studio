演唱会开票那一刻，你在 `ticket.example/buy` 点下购买，页面却弹出「系统繁忙，请稍后再试」。很多人以为网站坏了。其实很多时候，网站还在正常工作——它在入口拦住了多出来的请求。

> 说明：`ticket.example` 是文档专用的示例域名[^rfc2606]，不是现实中的购票网站。开票这一秒 10000 请求、处理能力 1000 请求／秒、挡回 9000、差 10 倍、对照中的 0 人／1000 人，以及文末讨论题里的十万请求，都是本例的示例数据，视频里出现的地方都标了「示例数据」或「示例」。这些数字不是任何网站的实测值，也不代表真实售票结果。

## 跟着这一秒的请求走一遍

### 1. 开票请求远超处理能力 {#spike}

{/* 配图：左「进来：10000 请求／秒（示例）」，右「处理能力：1000 请求／秒（示例）」，中间「差 10 倍」 */}

示例里，开票这一秒涌进来一万个请求，可网站一秒只能处理一千个，差了整整十倍。

要是这一万个请求一起涌进去，服务器会被挤垮，连原本能买到票的人也买不到了。

### 2. 入口限流：只放进处理得了的请求 {#gate}

{/* 配图：入口控量 → 每秒放行 1000（示例）→ 挡回超出的请求 */}

所以网站先在入口控量：一秒只放进处理得了的一千个请求，多出来的先当场挡回去。这种主动控制每秒放进多少请求的做法，就叫**限流**。每秒放多少，叫每秒请求数，简称 **QPS**。

在浏览器里能看到这一步。先打开开发者工具的「网络 Network」面板，列表是空的；再在购票页按「购买」，列表这时才出现 `buy` 这一行。点开它的「标头 Headers」，能看到状态码 `429 Too Many Requests`。RFC 6585 对 429 的说明是[^rfc6585]：

> "The 429 status code indicates that the user has sent too many requests in a given amount of time ("rate limiting")."

意思是：用户在一段时间内发了太多请求，被限流了。页面上写成「系统繁忙，请稍后再试」，这时候网站其实还在正常工作——已经放进来的请求照常往下处理，示例里这一秒仍有一千人能走到购票确认流程。

限流不是把网站关掉，而是让进来的量不超过处理能力，已经进来的人还能买成票。

Amazon API Gateway 用令牌桶做限流，文档原句是[^aws]：

> "API Gateway throttles requests to your API using the token bucket algorithm, where a token counts for a request."

超过稳态速率和突发上限时，客户端可能收到 429[^aws]：

> "When request submissions exceed the steady-state request rate and burst limits, API Gateway begins to throttle requests. Clients may receive `429 Too Many Requests` error responses at this point."

令牌桶的算法细节视频里没展开，只作文章补充。片中状态码示例选用 429；不同实现返回码可能不同，见下文 Nginx 默认 503。

### 3. 对照不做限流，新的一秒再买 {#contrast}

{/* 配图：左「不做限流：0 人（示例）」，右「限流：1000 人（示例）」 */}

同样这一秒，不做限流可能一个人都买不成，做了限流至少还有一千人能顺利走到确认。

示例里，入口每秒放行一千个，多出来的九千个当场被挡回去，下一秒再重新开始算。这期间你稍等一下，新开标签页重新打开购票页，等到了新的一秒，入口又有空位了。这次先打开开发者工具，再点一次购买，这一行的状态码已经是 200，页面显示可以下单。

### 4. 被挡回以后别狂点 {#mash}

那刚才被挡回去以后，一直狂点购买有用吗？没用。每点一次就是一个新请求，还得跟别人抢同一秒的名额，稍等一下再点更好。

消息队列把多出来的单先排着慢慢处理；限流则是在入口就挡住多出来的请求。这两招常一起用：入口先控量，放进来的请求再排队慢慢处理，高峰时刻才扛得住。上一期讲消息队列，这一期讲限流，合起来就是网站扛住高峰的两招。

回到开场，你看到系统繁忙，很可能是网站正在限流，好让已经进来的人还能顺利买成票。

## 视频里没讲的几件事

**页面写「系统繁忙」，不一定就是限流。** 繁忙文案是网站自己写的，也可能是后台故障、维护或别的暂时不可用。片中只演示限流返回 429 的一种情形；单看文案，分不清到底是哪一种。

**503 与 Nginx 默认。** Nginx 的 `limit_req` 用漏桶限流，文档原句是[^nginx]：

> "The limitation is done using the "leaky bucket" method."

默认拒回状态码是 503：`limit_req_status 503;`，文档写「Sets the status code to return in response to rejected requests.»[^nginx]。RFC 9110 对 503 的说明是[^rfc9110]：

> "The 503 (Service Unavailable) status code indicates that the server is currently unable to handle the request due to a temporary overload or scheduled maintenance, which will likely be alleviated after some delay."

所以限流挡回也可能返回 503，并不只有 429。片中选用 RFC 6585 的 429 作限流示例，503 只写在文章里，不上屏、不口播。

**并发数、配额、熔断与降级。** 限流还可以按并发连接数或配额（一天多少次）来定，不只 QPS 一种；熔断、降级是另外两招，留给 EP.13／EP.14。

**被挡回以后别狂点。** 每点一次就是一个新请求，还得跟别人抢同一秒的名额；稍等新的一秒再点，往往更划算。

**自己看的时候，先打开开发者工具。** 先打开「网络 Network」面板，再按「购买」，否则请求可能在你打开面板之前就已经发完，列表里看不到那一行。

## 想一想

要是这一秒涌进来不是一万个请求而是十万个，入口还是一秒一千，要挡回去多少？评论区说说。

**参考答案：** 九万九千个（示例）。100000 − 1000 = 99000，前提是入口仍按每秒一千放行、这一秒只算这一批。

消息队列那边的问题，可以回看 EP.10 [《双十一下单那么多，为什么不丢单？》](/message-queue-v1)：下单先写进队列、马上回已提交，后台再按自己的速度处理。
