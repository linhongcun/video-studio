一盏灯只有亮、灭两个状态，不能直接列出100个人的名字。但如果让每个发信人最多成功开灯一次，再由固定的人逐一接收，这个小小的共享状态就能积累出“每个人都来过”的证据。

关键不在记住灯切换了多少次，而在每次切换由谁、在什么条件下完成。下面先推导为什么需要一次性发送和唯一计数员，再用四人的连续来访过程区分“已经来过”“成功发出”和“已被计数”；最后说明放大到100人后，安全性、最终完成与等待时间分别依赖什么。

## 条件与要确认的事 {#problem}

采用以下题面，改变其中的条件可能需要另一套协议：

- 共有100人，事先可以约定策略，此后相互隔离，不能交谈或留下其他标记。
- 每次只有一人进入同一处，能观察并改变一盏灯；灯的状态会保留，初始已知为灭。
- 每个人可以保留自己的记忆，不能直接看到其他人的来访或私有记忆。
- 进入顺序未知；保证每个人在无限延续的过程中都会被选中无限次，没有固定截止时间。
- 目标是最终有人能正确宣布：100个人都至少来过一次。无需所有人同时在场。

这里的公平条件说的是每个人以后仍会不断有机会进入，不要求每轮选人等概率，也不要求每隔多少次就轮到每个人。本文给出一套可行的协议，不比较哪套策略的平均耗时最短。

### 为什么不能直接数来访次数

某个人已经来过，又反复进房，来访总数仍会增加；另一人却可能一直没有来。累计100次进入，并不能推出100个人都来过。

要让数字代表不同的人，必须约束每人最多贡献一份，同时确保已经发出的贡献不会在接收前被覆盖。前一条需要个人记忆，后一条需要让灯亮时保留信号，并由固定的人接收。

## 约定谁发送、谁接收 {#protocol}

### 只选一名计数员

事先选0号为计数员，其余1—99号是发信人。计数员的累计值从0开始；他不向自己发信，只负责接收另外99人的贡献。

公开讨论中的单计数员方案同样先指定一个收集者。以下短引只支持事前选择这一角色；具体累计规则及本文的正确性论证在后面展开。

<SourceQuote sourceId="R1" supports="该原句支持事先指定一名收集者，即本文的唯一计数员；不将这一句当作99次阈值、安全性或等待时间的证明。" translation="游戏开始前，应先选一名囚徒担任收集者（计数员）。" />

约定只有计数员关灯：他看见灯亮，就关灯，并把累计值加1；看见灯灭，就什么也不改，累计值也不变。“只有计数员关灯”是大家事先遵守的行为约定，不是其他人没有关灯的物理能力。

### 发信人记住的是首次成功，不是首次进入

每名发信人只保存一个属于自己的记忆：是否已经成功发送。

| 本人的记忆 | 眼前灯态 | 本次动作 | 离开后的本人记忆 |
|---|---|---|---|
| 还未成功发过 | 灭 | 开灯，发出一份 | 已发 |
| 还未成功发过 | 亮 | 不动，等以后有机会 | 仍未发 |
| 已经成功发过 | 亮或灭 | 都不再开灯，也不关灯 | 仍已发 |

2010年的经典协议把非计数员的动作写成“第一次在灯灭时进入房间”才开灯，而其余时候不动。条件同时包含了本人尚未成功发送和眼前灯灭，不能缩成“第一次进房就用掉资格”。该历史文献在本文仅作参考。

<SourceQuote sourceId="R2" supports="Protocol 1的该连续原句描述非计数员首次在灯灭时进入才开灯，之后不再行动；它支持首次成功发送的一次性约束，不代表第一次进入时遇到灯亮也要消耗资格。" translation="他们首次在灯灭时进入房间，就把灯打开；其余时候不做任何事。" />

灯亮表示有一份尚未接收的贡献。未发送者看见亮灯时暂时不动，既保留这一份，也保留自己的发送资格。已经发送的人即使后来再看见灭灯，也不再开灯；这样才不会把同一个人算成两人。

画面为了方便理解，会同时显示每人的“未发／已发”教学标记。实际执行时，每个人只记自己的状态；计数员只看灯态并记累计份数，既不知道是谁开的灯，也不能读取别人的标记。

## 四个人完整走一遍 {#walkthrough}

先把人数缩成四人：0号计数，1、2、3号各发送一份，目标累计值相应变成3。以下12次来访是固定教学示例，不是随机试验，也没有重置灯态或个人记忆。

### 灯亮时，没有发出的人保留资格

初始灯灭、累计0，三名发信人都未发过。

1. 1号先来，看到灭灯，开灯并记住自己已发。灯亮了，计数仍是0，因为计数员还没接收。
2. 2号来时灯亮，保持不动，自己的记忆仍是未发。
3. 1号又来，已经发过，因此仍不动。三次来访之后，灯上依然只有一份待收信号。

这里不能把2号的第一次来访记成“发送资格已用”。他尚未将灯从灭改成亮，贡献还没有发出去。

<Figure src="/video-studio/episodes/prisoners-light/article/01.jpg" alt="四人教学例中，1号已成功开灯，2号遇到亮灯仍未发，3号也未发；共享灯亮，计数员累计仍为0" caption="一次成功发送之后，亮灯保存一份待收信号。2号遇亮只是在等待，自己的发送资格仍在；1号重访也不会多产生一份。" seekTo={87.7} chapter="walkthrough" n={1} />

### 接收后，成功发送的记忆仍然保留

第4次由计数员进来。他看到亮灯，关灯，累计从0变1。

第5次又是1号。这次灯虽然灭了，但1号自己的“已发”记忆没有清空，因此不能再次开灯。计数保持1，不会把1号重复计算。

第6次2号来，灯正好灭，终于成功开灯并记为已发。第7次3号来时又是亮灯，他继续保留未发资格，等待以后的机会。

此时四个人实际上都进入过了，但计数员还没有收到完整的证据。观众看见完整来访过程，不等于计数员也能看见；协议不能凭借观众的全知视角提前宣布。

### 计数员重复来访也不一定加数

第8次计数员接收2号留下的那份，关灯后累计变成2。第9次还是计数员来，但灯已经灭了，说明没有新信号，他不加数。

第10次3号终于遇到灭灯，开灯并记为已发。第11次仍是3号，已经发过，所以不动。此时三名发信人都发送过，但累计仍是2，最后一份还亮着等待接收。

第12次计数员看到亮灯，关灯后累计增加到3，才能宣布四个人都来过。每份来自不同发信人，说明其余三人都来过；而计数员本人此刻也正在场，证据完整了。

## 为什么安全、为什么会结束 {#guarantee}

### 放大到100人，为什么只数99份

保留同样规则，只把发信人从3名增加到99名。每个不同发信人最多成功开灯一次，而亮灯期间任何发信人都不改变灯，只有计数员会把它关掉并接收。因此，计数员每增加1，都对应一份此前尚未接收的、来自某个不同发信人的贡献。

累计99时，99名发信人都曾成功进入并开灯。计数员本人是在这次接收时宣布，也已经进入，所以100人都来过。要求他累计100份反而超出了协议能产生的99份，不能将计数员也当成一个发信人多等一份。

### 用一个不变量写清证据

令`S`为已经成功发送的非计数员人数，`C`为计数员的累计值，`L`在灯灭时取0、灯亮时取1。初始已知为灭，因此`S＝C＝L＝0`。协议始终保持：

```text
S = C + L
0 ≤ C ≤ S ≤ 99
```

- 成功发送时，灯原为灭且此人从未发过，`S`与`L`各加1，`C`不变。
- 接收时，灯原为亮，关灯使`L`减1，累计使`C`加1，`S`不变。
- 其余来访不改变三者。

所以灯亮时恰有一份已发未收的贡献；计数并没有在访问或等待中凭空增长。收到第99份并关灯后，`C＝99、L＝0`，故`S＝99`。所有99名发送者都进入过，再加上此刻的计数员，宣布安全。

这里的`S`是证明时使用的全知统计，不是计数员需要观察的变量。计数员只需执行自己的亮灭判断和累计规则。

### 公平保证最终完成，不提供统一等待上限

只要还没收满99份，就分两种情况：

- 灯亮：计数员在后续仍会进入，因此会在某个有限的后续时刻关灯并增加1。
- 灯灭：此时`S＝C＜99`，至少还有一人没发送。在下一次成功发送发生前，灯会一直灭；公平保证未发送者之后仍会进入，故下一份一定会发出，再由计数员接收。

这样每轮都能在有限的后续时刻收到下一份，有限的99份逐一收完，最终会宣布。这个推论不需要假定独立、均匀的随机选人。

但“每一轮最终会发生”不等于存在一个对所有合法进入顺序都适用的固定天数或访问次数上限。给定任意长度，可以先让计数员在灭灯状态下重复进入这么多次，然后再接上让所有人轮流进入的无限序列。这个顺序仍满足每人无限次再来的公平要求，却能把第一份信号任意推迟。因此本协议没有统一的有限完成时间上界。

### 哪些条件变化会使本协议失效

初始已知灭很关键：若初始亮，而计数员照样把它算成收到的一份，就会多出一份没有发送者的信号。本文的`S＝C＋L`也无法从初始状态成立。初始状态未知的题型需要另定协议，不能直接沿用这里的99阈值。

如果不再保证每个人未来仍会进入，尚未发送的人可能永远没有机会，或亮着的最后一份永远遇不到计数员，此时只能保持不误报，不能保证最终结束。若约定允许非计数员也关灯，待收信号就可能丢失；若已经发过的人允许再开灯，又可能把一人重复算成多人。

## 完整协议与有限模型核验 {#verification}

以下是本期协议的教学伪代码。`sentOnce`只属于当前发信人的私有记忆，计数员不能读取或遍历其他人的状态；`count`只由计数员保存。

```text
初始：灯灭，count = 0，每名发信人的 sentOnce = false

每次计数员进入：
    如果灯亮：
        关灯
        count = count + 1
        如果 count == 99：宣布所有人都来过
    如果灯灭：不动

每次某名发信人进入：
    如果本人 sentOnce == false 并且灯灭：
        开灯
        本人 sentOnce = true
    其余情况：不动
```

本期的[核验程序](https://github.com/linhongcun/video-studio/blob/main/episodes/puzzles/prisoners-light/production/verify_protocol.py)从规则生成全部可达状态，对2至8人的小规模模型执行穷尽检查：合计10916个状态、82639条转移，另对不变量、发送与接收归属等执行1122660项实例检查。4人主例的12次来访与上表使用同一份`model-data.json`数据。

这些有限执行支持相应范围内的协议和演示一致性，不替代前面对任意有限人数的归纳不变量和公平完成论证。程序中的100人、198次来访只是每次发送后立即让计数员接收的一条存在示例，不是最少次数、期望次数或所有顺序都必须达到的时长，也不是现实囚徒实验。

核验还保留了三个改坏规则的反例：首次来访遇亮也消耗资格，会让某人的贡献永久缺失；已发者可以反复开灯，会把同一个人算成多人；初始亮却照常计数，会制造没有发送者的一份。反例用于说明条件为何必要，不能当作正确协议的运行结果。

## 小结 {#conclusion}

一盏灯能够完成这个任务，是因为协议把“一个人的一次成功发送”与“计数员的一次接收”逐一对应起来。未发送者遇亮保留资格，已发送者以后不再开灯，唯一计数员关灯才增加1；这三条约束让累计值代表不同的人，而不是反复来访的次数。

在初始已知灭、各人遵守约定且每人会无限次再来的条件下，99份最终都会被接收；它们证明其余99人来过，正在宣布的计数员也来过。公平保证最终收齐，不能承诺一个固定的完成天数。
