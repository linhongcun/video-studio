## 为什么改一条规则要看整段 {#why}

活动价从八折改成七五折，只改一条计算规则，为什么又得打开结算函数？因为普通价、会员价、活动价都写在里面。结算既组织共同流程，又掌握每种优惠的计算细节。

先固定本片的教学规则：同一笔订单原价100元；普通付100元，会员付90元，活动付80元。**每次只选择一种，重新从100元开始算，优惠不叠加。** 这些金额和政策都是示例。

这段代码并没有天然错误。规则很少、很稳定时，它清楚而直接。需要进一步设计的信号是：各条规则开始独立变化，主流程却总与具体算法一起被修改和阅读。UBC 的课程建议先检查变化与痛点，再判断机制和成本，适合用来衡量这次拆分是否值得。[^ubc]

## 把算法交给可替换的规则 {#delegate}

把普通、会员、活动的计算分别提成函数，约定它们都接收原金额、返回应付金额。结算入口收到其中一个函数，再通过相同方式调用它。这就是本例的策略：**独立的可替换算法，由主流程委托执行。**[^strategy]

按图追一遍：调用方先选会员规则；结算把100元交给它；规则算出90元；90元回到结算。普通和活动规则没有在这次请求里执行。改选活动时先重置到原价100元，再得到80元。

选择逻辑仍然存在。它可能来自请求参数、配置或业务判断，本例放在调用方。将其移到外部，是明确职责，不是让系统无需作出选择。

策略可以通过对象接口实现，也可以像本例一样用函数。Python 官方排序接口能接收 `key` 函数，Java 的排序方法能接收 `Comparator`，都能帮助识别“稳定过程接收外部局部行为”这种结构。前者选择取键行为，后者选择比较规则，**都不能据此说成更换了整个排序算法**。[^python][^comparator][^arrays]

## 规则改变时，究竟改哪里 {#change}

把活动函数的八折改成七五折，再选择这个新版本。同一100元输入得到75元，结算函数和会员函数不需要随这次算法变化而修改。需要保持的是共同契约：金额单位、参数含义、返回值和错误规则都相容。

| 本例需求 | 实际需要改变 | 本次保持 |
|---|---|---|
| 活动八折改七五折 | 活动算法及调用侧采用的版本 | 结算入口、普通与会员算法 |
| 新增新客减10元 | 新函数、登记项及选择规则 | 已有结算调用方式 |
| 改为同时叠加多个优惠 | 重新定义组合、顺序与舍入 | 本片的单选结构不足以直接覆盖 |

下面是本期完整可运行的 Python 程序，与制作目录的 `demo/pricing.py` 一致。金额单位为**整数分**，百分比不足一分的部分向下取整。这是本例明确选择的教学规则，真实项目应按自己的金额与舍入要求设计。

```python
"""Single-rule pricing example for D01. Amounts are integer cents.

Teaching rules, not a production promotion engine: percentages round down to
one cent, one rule is selected, and no discounts are stacked.
"""

from collections.abc import Callable, Mapping

Pricing = Callable[[int], int]


def validate_total(total_cents: int) -> None:
    if type(total_cents) is not int or total_cents < 0:
        raise ValueError("total_cents must be a non-negative integer")


def ordinary(total_cents: int) -> int:
    return total_cents


def member(total_cents: int) -> int:
    return total_cents * 90 // 100


def campaign(total_cents: int) -> int:
    return total_cents * 80 // 100


def campaign_v2(total_cents: int) -> int:
    return total_cents * 75 // 100


def newcomer(total_cents: int) -> int:
    return max(0, total_cents - 1_000)


def before_checkout(total_cents: int, kind: str) -> int:
    """Original implementation: the checkout contains the concrete rules."""
    validate_total(total_cents)
    if kind == "ordinary":
        return total_cents
    if kind == "member":
        return total_cents * 90 // 100
    if kind == "campaign":
        return total_cents * 80 // 100
    raise ValueError("unknown pricing rule")


def checkout(total_cents: int, pricing: Pricing) -> int:
    """The stable context: validate, delegate, validate the result, return."""
    validate_total(total_cents)
    payable = pricing(total_cents)
    if type(payable) is not int or not 0 <= payable <= total_cents:
        raise ValueError("pricing must return integer cents within [0, total]")
    return payable


RULES_V1: Mapping[str, Pricing] = {
    "ordinary": ordinary,
    "member": member,
    "campaign": campaign,
}
RULES_V2: Mapping[str, Pricing] = {
    **RULES_V1,
    "campaign": campaign_v2,
}
RULES_EXTENDED: Mapping[str, Pricing] = {
    **RULES_V2,
    "newcomer": newcomer,
}


def select_rule(kind: str, rules: Mapping[str, Pricing]) -> Pricing:
    """The caller selects a rule. Selection has not disappeared."""
    if not isinstance(kind, str) or kind not in rules:
        raise ValueError("unknown pricing rule")
    return rules[kind]


if __name__ == "__main__":
    for name in RULES_V1:
        print(name, before_checkout(10_000, name),
              checkout(10_000, select_rule(name, RULES_V1)))
    print("campaign after update:",
          checkout(10_000, select_rule("campaign", RULES_V2)))
    print("newcomer:",
          checkout(10_000, select_rule("newcomer", RULES_EXTENDED)))
```

运行后，本例依次输出：

```text
ordinary 10000 10000
member 9000 9000
campaign 8000 8000
campaign after update: 7500
newcomer: 9000
```

`before_checkout` 保留重构前的写法；`checkout` 是稳定的结算入口；`select_rule` 是调用侧的选择。这个单文件程序同时保留活动旧版和新版，借助 `RULES_V2` 映射切换，方便直接比较结果。**它展示版本对照，不是“一处修改”的源码补丁。**

### 真正只改活动算法的补丁

制作目录另存了两份可独立运行的最小源快照：`demo/snapshots/before.py` 与 `after.py`。它们使用相同的 `campaign` 名字、相同的注册表和结算入口，实际差异只有：

```diff
 def campaign(total_cents: int) -> int:
-    return total_cents * 80 // 100
+    return total_cents * 75 // 100
```

两份源快照分别运行后，同一10000分输入的普通、会员、活动结果为 `[10000, 9000, 8000]` 和 `[10000, 9000, 7500]`。验证器还比较了解析后的代码结构：只有 `campaign` 函数节点改变，注册表、选择函数和结算函数均未改变。21组快照对照覆盖了整元和非整元输入；完整补丁与源散列保留在运行报告中。视频“本次只改活动”对应这组实际证据。

新客减免用 `max(0, total_cents - 1_000)` 防止小额订单出现负应付金额。未知规则直接拒绝，不悄悄回退为原价；策略返回浮点、负数或超过原价的金额，也违反本例契约。

## 什么时候值得多拆这一层 {#boundary}

可以先看三个具体条件：这件任务是否真的有不同算法；算法是否需要分别变化；它们能否遵守有意义的共同契约。满足这些条件时，拆开通常更容易定位每条规则，但阅读者也要从结算跳到具体函数，调用侧要维护选择与登记。

如果只有两条长期不变的简单判断，直接写清楚可能更省事。不要为凑模式引入一套空接口、工厂和类层次；也不要仅以 `if` 是否消失判断设计好坏。

读复杂项目时，可以沿着一个参数或接口追踪：**谁选出了实现，谁调用它，具体算法写在哪里？** 如果结算仍在内部自行判断所有规则，只是把分支搬进另一个大函数，算法的独立变化可能仍未建立。

策略与状态也需要按意图区分。本例在同一任务里选择一种计算方法；状态模式关注对象处于不同内部状态时如何处理操作，以及怎样迁移。两者可能出现相似的委托结构，不能只看类图或名字。[^state]

本片解释的是代码组织。资格校验、优惠叠加、税费、舍入、支付与并发仍需各自明确设计；策略模式不会自动解决这些业务问题，也不保证代码运行得更快。
