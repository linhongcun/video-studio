## 同一件事，为什么要换办法 {#why}

同一笔原价100元的订单，按会员办法计算，付90元；按活动办法计算，付80元。结算这件事没变，变化的是**怎么算应付金额**。

本片先只认识这两种办法：会员九折、活动八折。每次都重新使用原价100元，只选一种优惠；不会先算90元，再在90元上打折。金额和折扣都是教学示例。

最直接的写法，是在结算里判断：会员就执行九折计算，活动就执行八折计算。**只有这两条简单、稳定的判断时，直接写完全可以。**

现在考虑的是，两种计算办法需要各自维护，也需要按情况替换。它们如果都写在结算内部，改其中一种时就要进入包含其他规则的流程。要不要进一步拆分，应结合实际变化和维护成本判断。[^ubc]

## 两个函数，两种策略 {#delegate}

### 先认识一个“策略”

先单独看会员办法：收到原价，按九折计算，再返回应付金额。在这里，这一种独立的定价办法，就是一个**定价策略**。活动办法也是一个策略，只是计算方式换成八折。[^strategy]

下面只摘出两种计算；金额单位是**分**，10000分就是100元。完整输入校验放在后半部分。

```python
def member(amount):
    return amount * 90 // 100

def campaign(amount):
    return amount * 80 // 100
```

`member` 是会员函数，`campaign` 是活动函数。先记住它们分别代表哪种办法。

## 先选择函数，再执行计算 {#change}

### 交进去的是函数，不是已经算好的90元

调用结算的代码先选好会员办法，再把这个函数交给结算：

```python
checkout(10000, member)
```

这里的 `member` 后面没有括号，表示传入会员函数本身。函数可以像其他值一样作为参数传入；结算随后调用它时，才会算出9000分，也就是90元。Python 官方教程也用一个名字指向已有函数的例子，说明函数对象与调用结果的区别。[^functions]

| 写法 | 此刻表达什么 |
|---|---|
| `member` | 会员函数本身，一种计算办法 |
| `member(10000)` | 现在执行会员函数，得到9000分 |
| `checkout(10000, member)` | 把10000分和会员函数交给结算，由结算执行计算 |

### `pricing` 此时对应哪个函数？

再看结算内部的核心逻辑。**这是省略校验的讲解摘录，完整可运行程序在后文。**

```python
def checkout(amount, pricing):
    payable = pricing(amount)
    return payable
```

`amount` 接收原金额，`pricing` 接收这次选好的函数。刚才传进来的是 `member`，所以这次执行中，**`pricing` 指向的就是 `member`**；不是凭空多出一种叫“pricing”的算法。

沿着这次调用走三步：

1. 进入结算：`amount` 是10000分，`pricing` 是会员函数。
2. 执行 `pricing(amount)`：这次实际执行的是 `member(10000)`，算出9000分。
3. `return payable`：把9000分返回，得到应付90元的结果。

**先选择办法，再交给结算；结算调用以后，金额结果才出现。** 谁负责选择，代码里仍然有明确的位置。

本期还直接检查了函数执行时的对应关系：[调用记录](https://github.com/linhongcun/video-studio/blob/main/episodes-codex/strategy-pattern/demo/beginner-evidence.json)确认，传入 `member` 时 `pricing` 就是该会员函数，10000分得到9000分；改传 `campaign` 后对应活动函数，得到8000分。

### 现在只换一次办法

现在只换一次办法。先保留同一笔订单的原价100元，重新计算，这次传入活动函数：

```python
checkout(10000, campaign)
```

结算中的 `pricing` 这次指向 `campaign`。执行的仍是同一句 `pricing(amount)`，但这次实际执行 `campaign(10000)`，返回8000分，也就是80元。

| 这一次交入的函数 | 结算内部怎样调用 | 实际执行 | 本次结果 |
|---|---|---|---|
| `member` | `pricing(amount)` | `member(10000)` | 9000分，90元 |
| 换成 `campaign` | `pricing(amount)` | `campaign(10000)` | 8000分，80元 |

两次输入都是10000分。第二次不是对先前的90元继续打折，而是**清楚地更换函数，再从原价重算**。

能保持同一种调用方式，是因为两个函数遵守相同约定：接收原金额，返回应付金额；单位和含义也一致。若一个返回金额、另一个却返回折扣率，就不能不加调整地互换。

## 什么时候值得这样拆分 {#boundary}

回头看本例，调用结算的代码负责选办法，结算负责调用，具体函数负责计算。**把同一任务的不同办法分开，让共同流程按统一约定使用选中的一种，这就是这里的策略模式。**[^ubc][^strategy]

重点不只是把代码提成几个函数，还在于结算能够接收并使用可替换的函数。阅读项目时，可以追踪三个具体问题：谁选出了函数？参数现在指向谁？真正的计算写在哪里？

当不同算法确实需要分别维护、替换时，这样拆分有价值。它也增加了一层调用关系，读代码时需要从结算跳到具体函数，调用侧还要维护选择逻辑。若只有两条长期不变的简单判断，保持直接写法通常更省事。不能只看 `if` 有没有消失来评价设计。

到这里已经完成本片主线：**会员函数交给结算得到90元，改传活动函数得到80元，结算沿用同一种调用方式。** 接下来是实现拓展，可以在理解这条主线后再读。

### 实现拓展：完整整数分代码与校验

以下内容不是视频里的新步骤。为了保留完整实现和变更对照，程序还包含普通原价、活动七五折新版、新客减免、登记表和错误校验。它们是进一步练习，不需要同时记住才能理解前面的两次调用。

金额使用非负整数分；本例百分比不足一分的部分向下取整。`checkout` 同时校验输入和策略返回值，不能把上面的三行核心摘录直接当作完整生产实现。以下代码与制作目录的 `demo/pricing.py` 逐字一致。

```python
"""Single-rule pricing example for D01. Amounts are integer cents.

Teaching rules, not a production promotion engine: percentages round down to
one cent, one rule is selected, and no discounts are stacked.
"""

from collections.abc import Callable, Mapping

Pricing = Callable[[int], int]


def validate_total(total_cents: int) -> None:
    if type(total_cents) is not int or total_cents < 0:
        raise ValueError("total_cents must be a non-negative integer")


def ordinary(total_cents: int) -> int:
    return total_cents


def member(total_cents: int) -> int:
    return total_cents * 90 // 100


def campaign(total_cents: int) -> int:
    return total_cents * 80 // 100


def campaign_v2(total_cents: int) -> int:
    return total_cents * 75 // 100


def newcomer(total_cents: int) -> int:
    return max(0, total_cents - 1_000)


def before_checkout(total_cents: int, kind: str) -> int:
    """Original implementation: the checkout contains the concrete rules."""
    validate_total(total_cents)
    if kind == "ordinary":
        return total_cents
    if kind == "member":
        return total_cents * 90 // 100
    if kind == "campaign":
        return total_cents * 80 // 100
    raise ValueError("unknown pricing rule")


def checkout(total_cents: int, pricing: Pricing) -> int:
    """The stable context: validate, delegate, validate the result, return."""
    validate_total(total_cents)
    payable = pricing(total_cents)
    if type(payable) is not int or not 0 <= payable <= total_cents:
        raise ValueError("pricing must return integer cents within [0, total]")
    return payable


RULES_V1: Mapping[str, Pricing] = {
    "ordinary": ordinary,
    "member": member,
    "campaign": campaign,
}
RULES_V2: Mapping[str, Pricing] = {
    **RULES_V1,
    "campaign": campaign_v2,
}
RULES_EXTENDED: Mapping[str, Pricing] = {
    **RULES_V2,
    "newcomer": newcomer,
}


def select_rule(kind: str, rules: Mapping[str, Pricing]) -> Pricing:
    """The caller selects a rule. Selection has not disappeared."""
    if not isinstance(kind, str) or kind not in rules:
        raise ValueError("unknown pricing rule")
    return rules[kind]


if __name__ == "__main__":
    for name in RULES_V1:
        print(name, before_checkout(10_000, name),
              checkout(10_000, select_rule(name, RULES_V1)))
    print("campaign after update:",
          checkout(10_000, select_rule("campaign", RULES_V2)))
    print("newcomer:",
          checkout(10_000, select_rule("newcomer", RULES_EXTENDED)))
```

运行后，本例依次输出：

```text
ordinary 10000 10000
member 9000 9000
campaign 8000 8000
campaign after update: 7500
newcomer: 9000
```

这里的 `Pricing = Callable[[int], int]` 用于表达“接收整数、返回整数”的函数类型；它不会自动完成业务校验。真正的金额范围检查仍由函数体执行。`select_rule` 是完整程序里的调用侧选择入口，选择责任没有因为引入策略而消失。

### 实现拓展：七五折和新客规则会改哪里？

下面再讨论新的需求，不与前面视频中的“只更换一次办法”混在一起。

| 后续需求 | 实际需要改变 | 本例可保留的部分 |
|---|---|---|
| 活动八折改七五折 | 活动算法 | 结算入口、其他算法及共同调用方式 |
| 新增新客减10元 | 新函数、登记项及选择规则 | 已有结算调用方式 |
| 改为叠加多个优惠 | 重新定义组合、顺序与舍入 | 本片的单选结构不足以直接覆盖 |

完整单文件程序用 `campaign_v2` 与 `RULES_V2` 同时保存两个版本，方便比较；这是版本演示，不是“一处修改”的源码补丁。

制作目录另存了 `demo/snapshots/before.py` 与 `after.py`：保留同名 `campaign`、相同注册表与结算入口，实际差异只有：

```diff
 def campaign(total_cents: int) -> int:
-    return total_cents * 80 // 100
+    return total_cents * 75 // 100
```

两份快照对同一10000分输入，活动结果分别为8000分和7500分；已有验证报告中的21组快照对照与代码结构比较确认，唯一改变的顶层函数是 `campaign`。这解释的是“修改一个算法”的范围，不意味着增加任何功能都无需修改其他代码。

新客减免使用 `max(0, total_cents - 1_000)`，避免小额订单出现负应付金额。未知规则明确拒绝；返回浮点、负数或超过原价的金额，也违反本例约定。

在真实接口里，也可以寻找“稳定过程接收外部行为”的关系。Python 的排序接口接收 `key` 函数，Java 的排序接口接收 `Comparator`：前者选择取键行为，后者选择比较规则，都不能据此说成更换了整个排序算法。[^python][^comparator][^arrays]

策略与状态还需要按意图区分。本例为同一个定价任务选择不同办法；状态模式关注对象内部状态变化时怎样处理操作与迁移。两者可能采用相似的委托结构，仅看类图或名字不足以判断。[^state]

资格校验、优惠叠加、税费、支付和并发仍需各自设计；策略模式不会自动解决这些业务问题，也不保证运行得更快。
