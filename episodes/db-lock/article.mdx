## 最后一件怎么通过两次 {#hook}

商品7042的库存是1，甲乙各要1件，数字均为教学示例。视频用数据库记录和请求直接演示，不复刻完整商城或支付系统。

上期的事务保证本笔修改如何共同确认；多个事务同时访问同一记录，还需要协调读取和修改的顺序。本期只讲“丢失更新”和“行锁”。

## 两次读取同一个旧值 {#stale}

错误流程是：甲乙分别普通查询，各自得到旧库存1；程序各算1−1=0；甲写回0、提交，乙又按自己的旧读取结果写回0。程序错误地放行两次购买，库存变化只反映一次扣减。

这里的错误是**把旧读取值算出的绝对结果写回，并据此放行**。不是说UPDATE不加锁；InnoDB的UPDATE本身也会锁记录，但不会自动修复应用已经算好的旧结果。相同值写回可能并未改变数据；程序不应把“SQL没有报错”当成业务扣减成功。[^set]

## 先加锁，再检查修改 {#locking}

以MySQL 8.4.0所属长期支持系列的InnoDB为背景，主键id精确定位一个已经存在的商品记录。在**同一个显式事务中**先加锁读取，再检查库存，执行修改，最后提交。FOR UPDATE是加锁读取，返回最新可用数据；已有冲突锁时默认等待。[^read]

```sql
START TRANSACTION;
SELECT stock FROM goods WHERE id = 7042 FOR UPDATE;
-- 应用检查返回值：stock >= 1 才继续，否则回滚并返回缺货。
-- 以下更新仅在检查通过的分支执行：
UPDATE goods SET stock = stock - 1 WHERE id = 7042 AND stock >= 1;
-- 还应检查实际更新结果，并在同一事务内处理所需业务数据。
COMMIT;
```

以上是流程示意，分支检查和异常处理必须由应用实现，注释不是可直接执行的完整购买程序。单行条件扣减也是可用的实现方向，需检查更新结果；视频选择加锁读取，是为了把检查过程演示清楚，并非宣称只有这一种正确写法。

## 等待后读取新库存 {#fresh}

甲先获得本例冲突锁，乙的加锁查询尚未返回。甲提交后，锁释放，乙继续并读取到0，程序据此判定缺货，不扣减、不放行，再结束自己的事务。提交或回滚都会释放该事务的相关锁。[^auto]

“等过了”不等于“可以购买”。如果等到锁后仍拿早先普通查询的1继续算，就失去了这套流程的关键保护。视频也不承诺谁先到达一定先获得锁。

## 锁与业务检查各管什么 {#recap}

锁协调冲突访问，库存是否足够是业务检查。应用还需正确处理事务失败、超时、重试与其他业务条件，不能只加一把锁就认为不会出错。

### 普通查询、锁定范围和更多术语

常见隔离级别下的普通一致性读使用快照，不等于FOR UPDATE，因此“有行锁时任何查询都不能读”不成立。SERIALIZABLE等情况另有规则。[^snapshot]

InnoDB记录锁实际锁定索引记录。本例采用主键精确查找已存在记录；范围扫描、非唯一条件、缺少合适索引，都可能扩大相关锁定范围，不能推广为“只要WHERE只写一个商品，就只锁这一行”。读锁/写锁、表锁、间隙锁、意向锁、悲观/乐观方法均不在画面展开。[^locks]

### 等待失败与死锁

等待可能超时，多条记录互相等待也可能死锁；错误处理取决于具体原因和配置，有时只撤销失败语句，有时整笔事务回滚。程序应明确结束或重试相应事务，保持事务短小、访问次序一致。视频不演示具体超时秒数，也不声称等待必定成功。[^error][^dead]
