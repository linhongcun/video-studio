# 《可靠消息：Outbox怎样把通知送出去？》

2026-10-24，按用户最新反馈将每种常见实现单独做短视频。本期只讲Outbox这一个可靠消息具体做法，不混事务消息或其他分布式事务路线。

- 14镜28句；目标约90–150秒，以实际配音为准，不变速压缩。片外文章保留实现边界和异常责任。
- 示例：订单8124、通知E8124、商品7042库存4买1；所有数字是教学示例，明确标“示例数据”。订单“已记录”不是整单成功。
- 核心首次标签只有Outbox和幂等，均从句首实测声学起音。其他标题用白话。无比喻、实物、假应用壳，深色全屏canvas。
- 订单+待办是生产端一笔本地事务；库存+唯一处理标记是消费端另一笔本地事务；两边与队列不能画成一个原子提交。
- 各失败/回看分支均明确重置，既有状态不能被新分支叙述偷偷改写。研究与官方依据见research.md。

### 01 hook

frame：canvas
章节：一条通知，卡住整笔业务
画面：首帧订单8124已记录、库存商品7042仍4，标题“订单记了，通知却丢了？”；发通知路径运行到一半中断，库存未变化；示例数据角标，不把订单已记录写成整单成功。
旁白：订单已保存，发通知前程序却停了。库存还没扣，这笔业务悬在了中间。
屏幕文字：示例数据；订单8124；通知E8124

### 02 outbox

frame：canvas
章节：先把待办一起保存
画面：Outbox首词起音才出现标签。共同边界包住订单记录和通知E8124待办；库存先退为上下文，指明这笔事务只管订单库。
旁白：Outbox，把要发的通知先记进订单库。订单和这条待办，用同一笔本地事务保存。
屏幕文字：示例数据；订单8124；通知E8124

### 03 write

frame：canvas
章节：先把待办一起保存
画面：订单8124候选行先进入，随后E8124/扣1件候选待办进入，两者金色待提交；共同边界不跨队列。
旁白：先写订单，再写一条扣库存的待办。现在两条记录，都还没有提交。
屏幕文字：示例数据；订单8124；通知E8124

### 04 commit

frame：canvas
章节：先把待办一起保存
画面：订单与待办同帧由待提交变青色已保存。随后程序路径淡出并显示中断，两条持久记录保留；订单整单仍待确认，不变成已完成。
旁白：两条记录一起提交，才算保存完成。程序随后即使停下，待办也还在库里。
屏幕文字：示例数据；订单8124；通知E8124

### 05 rollback

frame：canvas
章节：先把待办一起保存
画面：另起失败分支明确重置：订单尚未保存、无待办。订单候选后待办写入失败，两条待提交记录一起撤销，队列没有通知。
旁白：换个失败分支，待办写入失败。整笔事务回滚，订单也不会单独留下。
屏幕文字：示例数据；订单8124；通知E8124

### 06 relay

frame：canvas
章节：发送与重发是下一步
画面：明确返回成功分支：订单与E8124已保存。订单缩退左上持久上下文，待办E8124移到焦点，发送程序读取候选，不删源待办。
旁白：回到提交成功的分支，待办仍保存在库里。后台发送程序接手，读取这条待办。
屏幕文字：示例数据；订单8124；通知E8124

### 07 send

frame：canvas
章节：发送与重发是下一步
画面：E8124沿路径进入消息队列，队列确认返回后，本地待办才变已发送。标注发送与标记是两个步骤，不能同步当一个跨系统事务。
旁白：它把通知发给消息队列，等队列确认接收。确认以后，再把本地待办标为已发送。
屏幕文字：示例数据；订单8124；通知E8124

### 08 crash

frame：canvas
章节：发送与重发是下一步
画面：明确回看故障分支：队列已持有E8124，本地待办仍待发送。确认途中或标记前中断，程序退出，持久待办不消失。
旁白：现在回看一个故障点，队列已经收到了通知。发送程序还没标记就停了，待办看起来仍没发过。
屏幕文字：示例数据；订单8124；通知E8124

### 09 redeliver

frame：canvas
章节：发送与重发是下一步
画面：程序恢复，读取同一个E8124并再次发出。队列只阶段性显示第一次和重发的同ID两条实例，库存未消费仍4；不能暗示新ID或新业务。
旁白：程序恢复后，会再次发送同一条通知。所以通知可能重复到达，不能到一次就扣一次。
屏幕文字：示例数据；订单8124；通知E8124

### 10 consume

frame：canvas
章节：库存与处理标记共同提交
画面：焦点移到库存库独立本地事务，接收E8124、唯一标记候选与库存拟改3；共同提交点库存4→3和E8124已处理同帧确认，队列在边界外。
旁白：库存端处理时，把扣减和处理标记放进同一笔事务。库存从四变三时，这条通知也记为已处理。
屏幕文字：示例数据；订单8124；通知E8124

### 11 consumer-rollback

frame：canvas
章节：库存与处理标记共同提交
画面：明确消费失败分支重置库存4/无标记；候选扣减和唯一标记因中途失败一起退出；随后同E8124再来并共同完成为3与已处理。
旁白：换个消费失败分支，两处修改共同回滚。通知再来时，可以重新尝试这一次扣减。

### 12 dedup

frame：canvas
章节：库存与处理标记共同提交
画面：句首起音显示幂等；回到已处理状态库存3/标记E8124保存，同一ID消息再次抵达唯一标记检查被识别为重复；不再出现-1操作，库存始终3。
旁白：幂等，让同一条通知重复到达，也只产生一次效果。已经处理过就返回结果，库存仍是三。
