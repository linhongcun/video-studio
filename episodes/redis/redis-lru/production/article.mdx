## 内存满了，怎样选键 {#memory}

Redis 作为缓存时，保存着一份可以重新加载的数据副本。达到配置的 `maxmemory` 限制后，系统需要按淘汰策略腾出内存。选择较久未访问的键，是希望把更可能再次被访问的数据留住；这只是对未来访问的预测，并不是保证。

先固定一个小例子。当前时刻为100，八个键的最近访问时刻是 A10、B20、C30、D40、E50、F60、G70、H80。因此它们的空闲时间分别为90、80、70、60、50、40、30、20。数字是教学时间单位；视频以秒展示。所有键都没有 TTL，容量图把等大键画成八格。真实 Redis 比较的是内存字节，不能把它理解为固定“只能存八个键”，也不能据此推导每写一个键一定只删一个键。

精确 LRU（Least Recently Used，最近最少使用）可以维护一条完整的最近访问顺序。若按这个规则选，A位于最旧端。但 Redis 的 LRU 是近似的：它抽取少量键，估算这些键空闲了多久，再从已见候选中找较旧者。没有被抽到的 A，并不因为在全局上最旧就一定入选。

<SourceQuote sourceId="R1" supports="官方文档明确Redis使用近似LRU，随机抽少量键后按较长空闲时间选择，不能将局部候选等同于全局精确排名。" />

这里的内存淘汰与 TTL 到期是不同机制。`allkeys-lru` 的候选范围是符合条件的全部键，不要求键设了过期时间；`volatile-lru` 只从带过期时间的键里选择。`noeviction` 则不以删键腾空间，可能拒绝需要更多内存的写入。这些策略不能混成一套。

## 从抽样到候选池 {#sampling}

本期实现范围固定为 **Redis 8.4.0**，官方提交 `60ba86f3c8b4e1ec96451171753a0a38e5c45a0c`。`src/evict.c` 的 `estimateObjectIdleTime` 以压缩时钟估算空闲时间；`evictionPoolPopulate` 为采样取得的键计算分数，再按分数放入候选池。代码中的 `EVPOOL_SIZE` 是16，较大的空闲分数放在更靠近取出端的位置。

为了看清动作，动画将 `maxmemory-samples` 设为3，并预设第一轮抽到 C、D、E。它们的空闲值为70、60、50，放进空池后，C成为池里最旧的候选。填池不会把真实数据从缓存搬走；池项只保存键的身份、所在数据库/槽以及采样时的分数。

随后从池的较旧端取候选，确认真实的 C还存在，再删除 C来释放内存。新键 I进入示意容量中，而 A仍保留。这正是“抽到的最旧”和“全局最旧”的差别。预设样本是用来解释机制的确定例子，并非声称实际 Redis 的随机数曾按 C、D、E 的顺序运行。

## 候选为什么跨轮保留 {#retained}

Redis 不会在每次淘汰后把候选池清空。第一轮选择 C后，D60与E50仍可以作为后续候选。再需要释放内存时，系统会补进新的样本，然后从合并后的候选中取较旧者。源码注释明确说明，这一组较好的候选会保留到后续 `performEvictions()` 调用。

<SourceQuote sourceId="R2" supports="固定版本源码说明候选跨performEvictions调用保留，并按idle值升序放置；它为后续选择保留之前见过的较好候选。" />

第二轮预设新样本为 F40、G30、H20。与池中已有的 D60、E50合起来比较，D仍拥有最大的采样分数，所以这次会选择 D，尽管 D不在第二轮的新样本里。保留候选增加了利用过去抽样结果的机会，却没有把全局没见过的 A自动纳入比较。

<Figure src="/video-studio/episodes/redis-lru/article/02-retained.jpg" alt="新样本F40、G30、H20与保留候选D60、E50合并，D60仍在候选取出端。" caption="教学示例：第二轮胜出的是上轮保留的D，并非这轮新抽到的键。" seekTo={95.73333333333333} chapter="retained" />

视频的连续两轮放在同一粗粒度时钟内，期间不插入其他读取，因此显示的分数没有改变。**池里的空闲值是采样时记录的值，不是一张每时每刻重新排序的实时榜单。** 实际 Redis 在再次使用旧池项时，并不会先重算池内所有键当前的空闲时间。读过某个候选后，它的旧池记录仍可能存在；近似性也包括这类陈旧信息。

同一个键还可能在不同采样里重复出现。源码填池不是一个按键名自动去重的精确集合；本片两轮选取互不重叠的样本，是为了把保留机制讲清楚，不能推广为真实抽样不会重复。

### 键已经没了，旧候选怎么办

候选记录与真实键的寿命可以不同。例如，应用先删除 E，旧池项 E50仍在。单独这次 `DEL` 已经腾出了内存，不会因此立刻多删一键。画面中的后续条件是：先由新写入 K用完腾出的空间，之后再写 L，需要继续淘汰；补进的新样本 I、J、K的采样分数均为0，所以不会排到旧 E50之前。

这时从取出端检查 E，发现真实键已不存在，便跳过这个失效记录，再尝试下一个候选 F。源码称这类记录为 ghost。跳过池项不会再从数据集中删除同一个 E，也不会重复统计它释放的内存。

## 近似与配置的边界 {#boundary}

`maxmemory-samples` 决定抽样数量。官方文档给出的示例配置是5；本片用3只是教学配置。增加采样数通常提供更多发现旧键的机会，但要检查更多样本，因此付出额外 CPU 成本。是否能改善自己的命中率，应以实际负载观察，不能用一次固定样本或随机运行结果推出所有场景都获益。

<SourceQuote sourceId="A2" supports="官方文档将增加采样量与CPU成本及观察实际缓存未命中率并列说明，不构成所有负载上的收益保证。" />

近似 LRU 也不等于 LFU。LRU关注最近一次访问距今多久；LFU用带概率的计数与衰减来估计访问频率，曾经的热点也可能随时间降温。不能把 LFU说成每次访问都精确加一、永不遗忘历史，也不能把 TTL 最早到期当作 LRU 最久没访问。

本片的有限模型和实际 Redis运行各有不同用途。`model.py` 明确给定样本，验证保留候选、失效记录和容量示意；它不运行 Redis字典的随机采样。`runtime_verify.py` 使用同一固定版本的真实进程，以 `allkeys-lru`、无 TTL 和 `maxmemory-samples=1` 记录可观察的键删除与统计。产品实测不暴露内部抽样顺序，不能用它来冒充动画预设样本的真实回放；两者均不是吞吐或时延基准。

## 小结

Redis近似LRU的路径是：需要释放内存，抽取部分键，按采样分数更新保留候选池，检查候选对应的键是否仍存在，再删除选中的实际键。它控制了维护成本，也利用了跨轮的较好候选；代价是每次选出的键仍不保证是全局精确排名中的最旧者。
