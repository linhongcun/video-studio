# Redis 近似 LRU：为什么未必淘汰真正最久没用的键？

EP52 / `redis-lru` / Redis 系列。制作基线 `01cd181caf24d4a8ce846c0eb8faeeab8f0054e2`。

唯一问题：Redis 为了控制维护成本，用抽样和跨轮候选池选择淘汰对象，为什么仍不能保证选中全局最旧的键？

画面约定：1920×1080、30fps，冷银灰/Redis红/石墨文字，全屏机制画布；同一组 A–H 键、同一轮访问时间贯穿。所有数字均为教学示例；八个等大键的“容量八格”仅为可视化，真实 maxmemory 比较字节。样本序列预先固定，非真实 Redis 随机采样回放。正文不展示浏览器壳或源码大页。首屏直接显示 A 空闲90秒与 C 空闲70秒，悬念是删 C 而保留 A。

源依据：Redis 8.4.0，commit `60ba86f3c8b4e1ec96451171753a0a38e5c45a0c`；官方 Key eviction 固定文档快照。池真实大小16项；动画只放大已占项，原始空槽作16格细条。示例将连续两次淘汰置于同一粗粒度时钟内，期间不插入其他读取，保留分数不变；不暗示每轮重算全部历史候选的时钟。

待独立审稿后才开始配音。以下旁白按每镜两句冻结，术语先有对象再命名。

### 1 problem
旁白：A九十秒没读，Redis却可能先删只空闲七十秒的C。内存满了，它凭什么选谁，为什么不保证删最旧的？
画面：八个键分布在同一条缓存行，A90红色虚线“全局最旧”，C70为候选红描边；写入I停在容量边界，C暂不消失。首帧已有主体与题名。
出处：R1 近似LRU段；R2 池的局部候选选择。首屏是待解释的教学结果。

### 2 capacity
旁白：先固定八个等大的键，示例容量已经用满，现在要写入I。所有键都没有设置到期时间，需要删键是为了腾内存，不是因为过期。
画面：八个等大键对应八格容量；I从右侧进入前停下。“示例容量8格；真实按字节”随容量显示；TTL栏统一“未设置”，不出现倒计时。
出处：R1 maxmemory与allkeys-lru；动画只解释容量动机，不承诺真实每写一键必删一键。

### 3 exact
旁白：先拿精确的最近最少使用策略作参照，按最近访问排出完整顺序。A最后一次被访问得最早，所以精确LRU会选择A。
画面：沿同一时间轴逐个建立 A10、B20、C30、D40、E50、F60、G70、H80，当前100；变为 H→G→F→E→D→C→B→A 的完整访问顺序。参照标签“精确LRU”在对象建立后显现，A被指明但不真正删除；下一镜明确返回同一未淘汰状态。
出处：R1 精确LRU比较；固定访问序列为本片原创教学数据。

### 4 approximate
旁白：持续维护完整顺序要付出成本，Redis采用近似LRU。它记录访问时钟，淘汰时随机抽一小批键，估计它们空闲了多久。
画面：精确参照整体收束；“回到同一组未淘汰的键”后保持 A–H，访问时钟变为空闲90/80/70/60/50/40/30/20；局部抽样框出现，未抽到的键仍清楚可见。
出处：R1 内存取舍；R2 estimateObjectIdleTime与evictionPoolPopulate。

### 5 sample
旁白：这里把每轮采样数设成三，第一轮恰好抽到C、D、E。A虽然更旧，却没进入这次比较。
画面：在原八键上按 C、D、E 的顺序落下三个抽样标记，三条带键名的路径从原位置伸向候选池；A仍留在未抽样位置。“samples=3 · 教学固定抽样”可见。
出处：R1 maxmemory-samples；R2 抽样后估算idle；不是概率或真实运行结果展示。

### 6 pool
旁白：这些样本按空闲值进入候选池，较旧的候选靠近取出端。当前池里C是七十秒，比D和E更旧。
画面：16格池从空开始；逐个插入 C70、D60、E50，放大已占项为 E50→D60→C70，右侧明确“取出端”。实际键与池条目分开，插池不移动/删除原键。
出处：R2 EVPOOL_SIZE=16与evictionPoolPopulate排序。

### 7 evict
旁白：确认C还存在，就把C从内存删掉，为I腾出位置。A仍然保留，因为本轮只能从已经见到的候选里选。
画面：C候选移向“存在检查”再指向原键C，C淡出并释放一格；I进入同一空格，原键A保持。“选C70 ≠ 全局最旧A90”结果停留。池里D60/E50保持，不清空。
出处：R2 从最大候选向前检查存在、从数据集删除；等大格仅示意腾空间。

### 8 retained
旁白：接着写入J，又需要腾出空间，这次先补进F、G、H三个新样本。上轮剩下的D和E还在候选池里，不会每次从空池重来。
画面：接续上一镜的I位置，J停在写入边界；F40/G30/H20从原键落入原池的空位。保留候选D60/E50用稳定深红边线，新样本用红色短闪，只有变化项移动。提示“连续两轮示例，期间无额外读取”。
出处：R2 across performEvictions calls与持久池。

### 9 reuse
旁白：合起来比较，旧候选D的六十秒仍然最大，于是这次选D。它甚至不在本轮的新样本里，候选池让先前见过的旧键还有机会被选中。
画面：池从左到右 H20→G30→F40→E50→D60，D从保留区走到存在检查，删掉数据集D并插入J。新样本F/G/H位置不变，全局最旧A90仍存活。
出处：R2 填池后取最大项；不存在全局精确性保证。

### 10 ghost
旁白：池中保存的是候选记录，键可能已经被别的操作删掉。真正使用候选时会检查它是否还在，失效记录被跳过，再找下一项。
画面：明确“另一个条件：应用先删了E”分支，从已展示池快照开始；原键E先消失，池条目E50保留为虚线；到使用时查找失败，划掉这条候选并移向下一个。此处不承诺把所有旧分数重新计算，也不画已删键再次释放内存。
出处：R2 ghost entry检查；与前两轮确定样本分支分开。

### 11 tune
旁白：增大采样数，更有机会看见较旧的键，也会增加检查样本的CPU开销。它不保证每次都选中全局最旧，更不保证任何访问模式下命中率都提高。
画面：返回第一次淘汰前的共同输入，标明“重新比较采样设置”；3个样本C/D/E与另一组5样本A/C/D/E/H并排，同一A90完整保留。仅示例说明发现A的机会，不显示命中率、性能倍数或普遍收益。
出处：R1 CPU取舍；本片不做性能基准。

### 12 recap
旁白：所以，Redis的近似LRU是在抽样和保留候选中优先找旧键。它控制维护成本，但不会为每次淘汰维护一份精确的全局排名。
画面：回收“访问时钟 → 随机抽样 → 保留候选 → 检查存在 → 删除腾空间”单条关系，少量状态随口播逐项出现；结尾显示“已见候选中的旧键”与A仍在的结果。品牌“IT小村 · 原创”简洁收束。随后独立5秒参考资料卡，正文字幕与人声在卡前结束。
出处：R1、R2；视频不展开LFU和其他策略分支。
