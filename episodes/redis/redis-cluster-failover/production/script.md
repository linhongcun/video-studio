# Redis Cluster：一个副本，怎样获得接管哈希槽的授权？

EP51 / Redis 系列 / issue #297。制作基线 `01cd181caf24d4a8ce846c0eb8faeeab8f0054e2`。

## 叙事与画面约定

唯一问题：旧主失联后，副本凭什么接管原来的槽？开头展示主甲失联、甲副本仍未接管的冲突，结尾兑现“多数主节点授权后，副本才带着新配置接管”。

三主三副本教学拓扑，每个主节点原来持有槽；主甲原槽0–5460、主乙5461–10922、主丙10923–16383。甲副本只复制主甲，不在三主选票分母中。示例轮次5→6不是产品实测轮次。完整范围为正常自动故障转移，禁用手工 FORCE/TAKEOVER；有限模型、实际进程实验和动画示意分别记录。

全屏机制画布，不用浏览器壳、比喻或无关实物。沿现行Redis冷银灰/红/石墨字与原始标识，真实EP51，不另编Redis期号。顶部保持稀疏位置提示“确认故障→请求授权→接管槽”；每次只展开当前动作，其他节点退为上下文。PFAIL/FAIL/currentEpoch/configEpoch随对应动作依次引入，不让完整内部名常驻。

每镜两句供共享句级装配。文字为正式字幕原文，TTS送模修订另记。正文收束后默认追加5秒两项原题/机构资料卡，资料无旁白、无正文字幕。图文保留源码、重试、数据新鲜度与多副本排名细节。

### 1 problem
旁白：主节点甲失联了，旁边明明还有它的副本。为什么这个副本不能立刻接管原来的数据？
画面：第一帧即主甲变灰、复制连接中断，甲副本旁的“接管？”保持问号；原槽徽标仍归主甲，不能在得到授权前搬走。乙丙暂退成背景身份。
出处：R1，Failure detection / Replica election and promotion。

### 2 topology
旁白：本例有三个主节点，各自负责一段哈希槽，每个主节点还有一个复制数据的副本。接下来只看主节点甲失联后，它的副本怎样接管甲的那段槽。
画面：三主各一段槽从左到右展开，下方副本与各自上方主节点连线；只高亮甲与甲副本的关系。槽是键空间归属，不画成一致性哈希环。
出处：R1，Key distribution model / Replica election and promotion。

### 3 suspicion
旁白：主节点乙发出探测，等过超时时间还没等到甲的回复。乙先把甲记为疑似故障，这只是乙自己的判断。
画面：探测脉冲乙→甲，无回包，乙的本地视图出现“疑似故障 PFAIL”；甲副本角色仍为副本，选票栏尚未出现。
出处：A1，Failure detection；R2，故障报告逻辑。

### 4 failure
旁白：乙还要收集其他主节点在有效时间内的故障报告。本例乙和丙都判断甲故障，达到三个主节点中的多数，才确认故障并传播出去。
画面：丙的有效报告到乙，乙的本地判断与丙报告明确标为“故障判断2/3”，随后FAIL状态传播至甲副本；报告不用选票形状或“授权”字样，避免与后面投票混淆。
出处：A1，Failure detection；R2，markNodeAsFailingIfNeeded。

### 5 eligibility
旁白：甲的副本收到确认故障后，还要检查自己能否参选，例如与旧主断开复制的时间不能过长。满足条件后先短暂等待；同一个主节点若有多个副本，复制进度会影响谁更早尝试。
画面：甲副本旁顺序显示“旧主已确认故障”“本例数据新鲜度合格”“等待后参选”三项，只有当前项放大；不凭空添加第二副本。排名差异只做右侧小注，不演出没有建立的竞争者。
出处：A3，Replica election and promotion / Replica rank；R2，clusterHandleSlaveFailover。

### 6 request
旁白：轮到甲的副本尝试时，它提高本次选举的轮次，再向主节点请求授权。图中从第五轮进入第六轮，旧轮次迟到的回复不能混进这一轮。
画面：甲副本轮次5→6，发出带“轮次6”的请求到三个原持槽主节点；甲离线无响应，乙丙可达。旧轮次回复用虚线停在轮次核验外，不计数。
出处：R1，Cluster current epoch / Replica election and promotion；R2，failover_auth_epoch与AUTH_ACK接收条件。

### 7 first-vote
旁白：只有持有槽的主节点能投票，副本不能给自己凑上一票。乙检查甲已确认故障、轮次也有效，投出本轮唯一的一票；一票还不够。
画面：副本侧标注“候选，不计自票”，乙的“轮次6尚未投”变“本轮已投”；乙→甲副本的授权回包抵达才使计数0→1，门槛一直显示“三个持槽主节点，需要2票”。
出处：R2，clusterSendFailoverAuthIfNeeded；R1，Masters reply to replica vote request。

### 8 majority
旁白：丙的授权回复也抵达，甲的副本才拿到三位主节点中的两票。多数按集群持槽主节点计算，不能因为甲离线，就把门槛降成一票。
画面：丙→甲副本的第二张授权回包抵达，计数1→2后出现“接管资格已获授权”；甲仍算原三主的分母，不能把只剩乙丙的在线数重算多数。
出处：R1，Replica election and promotion；R2，needed_quorum / failover_auth_count。

### 9 takeover
旁白：获得授权后，甲的副本提升为新主节点，接管甲原来负责的槽。它用更高的配置轮次宣布新的槽归属，其他节点收到后更新自己的记录。
画面：甲副本身份变“新主”，原0–5460槽归属徽标从旧主位置连续转交到新主；配置轮次6的通告抵达乙丙，其小型槽表同步更新。槽归属移动不能画成故障节点把缺失数据搬来。
出处：A4，Configuration epoch / Hash slots configuration propagation；R2，clusterHandleSlaveFailover成功分支与clusterFailoverReplaceYourMaster。

### 10 minority
旁白：再看一个独立对照：甲的故障已经确认，但投票时只有乙能回复。就算甲的副本也在这边，一张主节点选票仍不足两票，它不能自行接管。
画面：显式标“独立对照，重新从参选前开始”，旧主仍FAIL，甲副本恢复副本身份与旧槽归属；丙变为此次投票时不可达。只有乙回包，计数1/2停住，候选无自票、不晋升。
出处：R1，Replica election and promotion；R2，needed_quorum。

### 11 data-boundary
旁白：拿到多数授权，证明的是接管资格，不是所有业务写入都已复制。Redis采用异步复制，旧主最后确认的写入如果还没到副本，换主后仍可能丢失。
画面：回到已完成的成功分支并明确标注，聚焦旧主与新主的数据区：旧主离线保留“已确认但未复制”的末条，副本只有已复制记录；不无声抹掉旧主字节，不凭选票生成缺失数据。
出处：A2，Write safety。

### 12 recap
旁白：所以这次接管有两道不同的判断：先确认旧主故障，再由多数主节点授权副本。候选拿到足够选票后，才能以新的槽归属成为主节点。
画面：回收固定全局路径“确认故障→多数授权→发布新槽归属”，当前新主保持在甲副本原位置；分别用故障报告、授权回包、槽表三种对象回顾实际动作，结尾IT小村·原创。
出处：R1、R2；模型核对见model.py。
