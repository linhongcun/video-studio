# Agent Skills：一个Markdown文件，为什么能成为技能？

本期：Agent概念系列Skills，内部EP.30（当前最大已使用内部期号为29，最终发布时再核对）。不要求观众看已撤下的A01/A02；面向会基本编程、知道接口和提示词的开发者。唯一问题是：**把一项工作的方法放进Markdown文件，为什么会被称为技能，实际增加了什么？** 用同一次创建订单接口兼容审查，展示方法被发现、逐步加载及借助工具使用的机制，不比较模型智力或承诺效果提升。

示例固定：旧创建订单请求只有`sku`与`quantity`，新版接口定义新增必填`channel`（来源渠道）。画面逐步呈现变更位置、团队规则与本地字段检查结果；本地简化规则只能证明该示例旧请求缺少新必填项，不冒充真实业务HTTP响应或完整OpenAPI兼容性分析。

画面约定：1920×1080、30fps、深色干净canvas。首镜可用对应功能的审查对话建立使用场景，后续机制图不套浏览器或假文件管理器。全片同一份变更、同一项技能、同一份上下文连续推进。代码画面仅01的字段差异与05的技能入口节选；其余用信息卡、连线和结果摘要。没有装饰进度条，术语随对象引入，字幕始终独立在画面底部。

证据边界：片中机制按Agent Skills规范解释；加载/执行、当前上下文与磁盘资料分开。参考资料被读取后内容可进入上下文，预写脚本可经工具执行后只返回结果，不画源码自动全部进入模型。没有“任务结束自动卸载”的通用保证，不画上下文瞬间清空。技能名/描述用于发现不等于确定性触发，技能说明不等于可执行控制流。实际配套运行与模型使用范围由本期demo记录注明，不能由本稿推断已跑通某商业宿主。

### 01 hook
旁白：你让AI检查，接口新增必填字段，旧客户端还能不能用？把团队审查方法放进一个Markdown文件，为什么就成了技能？
画面：首帧标题明确为「Agent Skills · 一份Markdown为什么成为技能」，同时给开发者审查对话：「检查这次接口变更，旧客户端还能用吗？」。下方只显示创建订单这一项功能：旧请求的sku、quantity保留，新接口旁出现「新增必填：channel · 来源渠道」。用问号保留审查悬念，不先写成兼容/不兼容，也不展示虚构的无Skill错误回答。

### 02 prompt-load
旁白：把所有规程都塞进系统提示词，确实能让模型读到。可同一个助手还要写发布说明，不相关的细则也会占用上下文。
画面：从同一审查请求缩出当前上下文区域；接口审查与发布说明两份方法正文一并挤入，而本次只需要接口审查。保持当前请求和channel变更可辨，逐步突出发布说明这份无关正文占据的区域；这是信息组织对照，不显示编造的token节省比例或模型准确率。

### 03 catalog
旁白：Agent Skills换的是组织方式，把一项工作的方法和资料打成可发现的技能包。先看名称和描述，需要时再展开细节，不用先读完所有正文。
画面：明确标出「换成技能组织时 · 另一套初始配置」，从同一任务重新开始：两份完整正文保存在各自技能包中，当前上下文起步只放两个短小的名称/描述条目。不能把02中已读的正文画成运行中自动退出上下文；两种配置的对照切换必须可辨。以「名称＋描述」到「完整指引」的结构先给整体方向，再聚焦接口兼容审查条目；不出现自动提升模型权重或训练动画。

### 04 route
旁白：比如这项技能叫接口兼容审查，描述写清比较新旧接口、检查旧客户端会不会受影响。描述太泛，就可能选错或漏选，它不是可靠的开关条件。
画面：突出同一候选技能的描述「比较新旧请求字段，检查旧客户端兼容性」与本次需求的对应，其他候选降为低对比。短暂并列泛描述「处理代码问题」，显示范围重叠的虚线而非必然错误路径；明确是发现/选择机制，不把关键词等号画成确定性if条件。

### 05 instructions
旁白：选中以后，Agent读取技能入口文件，获得这项工作的具体指引。里面写清先比什么、查哪份规则、交出哪些证据，模型的训练参数并没有改变。
画面：当前候选条目展开到标明SKILL.md的入口卡，显示name/description和三条紧凑指引：「比较新旧请求字段」「按需读字段规则」「运行检查并报告证据」。正文由包进入当前上下文，包本体仍留在外部资料区；不用整屏YAML，不把说明文字直接变成自动执行箭头。

### 06 paths
旁白：技能包也不只有这一页说明，兼容规则和字段比较脚本可以分开存放。接下来要分清两条路径，参考资料拿来读，脚本交给工具运行。
画面：从同一技能包展开三个简单资源节点：入口、字段规则、检查脚本，不能套文件管理器。全局路径固定为左侧技能包、右侧当前上下文、下方宿主工具：参考资料有「读取」路径，脚本有「执行」路径，工具另有结果回传路径。先给总览停留再进入下一镜，三条路径不可全部同时运动。

### 07 reference
旁白：这次只检查请求字段，Agent按指引读取对应的兼容规则。新增必填的来源渠道字段会让旧请求缺参数，这条依据进入上下文，其他技能的正文暂时不用读。
画面：沿读取路径只展开请求字段规则，显示「对既有请求新增必填项 → 旧请求可能缺参」与本次channel变更的对应。来源规则内容进入当前上下文；未选中的发布说明技能包保持正文未读，不占当前上下文的正文区域。规则是本地示例的判断依据，不显示真实系统响应码或泛化为所有API的保证。

### 08 script
旁白：脚本走另一条路径，由宿主提供的工具运行字段检查程序。源码不必整段送给模型，实际检查结果再回到上下文。
画面：从总览定位下方执行分支，预写检查脚本连同旧字段定义、新字段定义、旧客户端请求三个输入进入宿主工具；源码节点停留在外部，不沿读取箭头灌进上下文。工具完成后，将结果卡「旧请求缺少channel」送回同一上下文；工具运行与结果返回依次发生，不让Markdown入口自己运行脚本。

### 09 evidence
旁白：检查发现，新接口多了一个必填字段，而旧客户端没有发送。Agent把变更位置、适用规则和检查结果合在一起，形成可复核的审查结论。
画面：回到首镜同一创建订单变更，不重置字段。channel标记、已读字段规则与本地检查结果三份证据依次归并，最后形成「本示例旧请求缺少新必填项，需要调整兼容方案」的审查摘要；标「本地简化校验」，不宣称覆盖完整协议兼容性或真实HTTP执行。

### 10 roles
旁白：这样就能看清，提示词承载指令，工具提供读文件或运行程序的能力。Skill把可复用的方法和资源组织起来，按任务逐步交给Agent使用。
画面：保留刚使用的入口指引、读文件/运行检查动作和技能包关系，分别落上「提示词：指令」「工具：能力」「Skill：方法包」标签。标签逐个对应既有对象，不新增三张脱离示例的术语定义表；强调包内说明会成为上下文中的指令，实际执行依赖工具。

### 11 limits
旁白：按需加载减少了无关正文，但发现索引也有开销，小技能包未必更省。内容怎样保留或压缩由宿主管理，资料仍要维护，审查结论也要核验。
画面：当前上下文稳定保留已读指引、规则与结果，不因任务结束自动清空。先突出目录中名称/描述也占上下文的「索引开销」，再沿同一信息关系突出「资料版本」与「结果核验」；规则卡显示版本来源，结论保留证据入口，不显示字节或token节省比例；小包未必更省，不追加一整套安全清单或不相关故障剧情。

### 12 closing
旁白：回到开头，Markdown只是技能入口，宿主让它能被发现和按需读取。连同配套资料与脚本，一套工作方法才能持续复用，而不必每次把所有说明贴进对话。
画面：回到开发者同一审查对话与可复核结论，再收束为唯一技能包的名称/描述、入口、按需资料及脚本关系；不重放一遍完整执行过程。只保留「发现方法 → 按需使用 → 证据可查」和品牌「IT小村 · 原创」，不追加下期预告、文章引流或大段代码卡。
