## 一份规程怎样成为技能 {#problem}

开发者要审查一次创建订单接口变更：旧客户端只发送`sku`与`quantity`，新接口定义新增了`channel`（来源渠道），并把它设为必填。旧客户端不改代码，还能不能使用新接口？团队已经有审查规程，要求检查约束变化、找出受影响请求，并给出可核对的证据。

把整份规程贴进提示词，模型当然能读到。问题出现在同一个助手还要承担发布说明等其他工作时：所有方法都常驻，就会把本次不需要的正文也送进上下文。这里比较的是两种人为选择的信息组织配置，**不是所有Prompt用法都必须全量常驻**，也不是先把正文读入后再自动卸载。

Agent Skills把工作方法打包成可发现的目录。按照当前开放规范，一个技能目录以`SKILL.md`为入口：YAML元数据中的`name`和`description`用来标识用途，正文写具体指引，还可以配套脚本、参考资料和模板等资源。这个结构让宿主和Agent可以先找到方法，再按任务需要读取细节。它没有修改模型权重，也没有使Markdown本身变成可执行程序。[^spec]

本期只围绕这一种变化展开：**一套工作方法怎样在适当时机，以适当粒度交给Agent使用。** 安装命令、API接线和通用Agent循环都不承担主线。

## 先发现，再展开方法 {#loading}

渐进加载可分成三个层次。它们说明内容进入模型上下文的时机，不等于底层磁盘读取的先后保证。[^client]

| 层次 | 给Agent看的内容 | 本例的作用 |
|---|---|---|
| 发现 | 候选技能的名称和描述 | 区分接口兼容审查与发布说明。 |
| 激活 | 选中技能的`SKILL.md`正文 | 知道先收集哪些输入、读哪份规则、怎样报告证据。 |
| 按需使用资源 | 相关资料，或工具执行脚本后的结果 | 只展开请求字段规则，并取得本次字段检查结果。 |

本地示例采用下面的组织方式：

```text
skills/
  api-compat-review/
    SKILL.md
    references/request-fields.md
    scripts/check_fields.py
  release-notes/
    SKILL.md
```

描述要能回答“什么时候应该用这项技能”。“处理代码问题”覆盖面太大；“比较新旧请求契约，检查既有客户端是否因必填字段变化受影响”提供的路由信息更充分。即便如此，**描述不是确定性的开关条件**：模型可能误选或漏选，用户也可以显式指定；具体的触发与加载方式取决于宿主。[^client]

选中后，入口正文给出一组工作指引：确认旧契约、新契约和旧客户端请求；按需读取规则；调用允许使用的工具运行检查；报告结论、依据及未检查范围。指引告诉Agent怎样组织工作，实际读文件、运行代码及处理错误仍需要宿主提供的能力。

## 读资料与跑脚本是两条路 {#resources}

参考资料和脚本不必以同一种方式使用。原始工程说明给出的重要设计是：Agent可以读取相关文本，也可以经工具运行预写脚本，让执行结果回到上下文，而无需先把脚本全文送给模型。这里说的是“可以不读全文”，不是禁止Agent在需要时检查源码。[^engineering]

本例的两条路径分别是：

```text
参考规则 → 文件读取 → 规则文本进入上下文
预写脚本 + 旧契约 + 新契约 + 旧请求 → 工具执行 → 检查结果进入上下文
```

脚本必须同时拿到旧字段定义、新字段定义和旧请求，才能分别给出契约级变化与该请求受到的影响。只看到“新增了字段”还不足以判断：新增可选字段和新增必填字段，会产生不同的检查结果。

| 相同的旧请求 | 新契约变化 | 本地检查结果 | 能下的结论 |
|---|---|---|---|
| 只有`sku`与`quantity` | 新增可选`channel` | 没有新增必填项，旧请求通过本例校验 | 通过已检查的必填字段规则。 |
| 只有`sku`与`quantity` | 新增必填`channel` | 新增必填项为`channel`，旧请求缺少它 | 该变化破坏了本例旧请求的必填字段约定。 |

主分支的工具结果保留三个关键事实：

```json
{
  "newRequiredFields": ["channel"],
  "oldClientValidation": {
    "missingRequiredFields": ["channel"]
  },
  "verdict": "breaking_required_field_change"
}
```

审查结论应把字段变更、团队规则与这份检查结果对应起来，而不是仅说“技能已加载”或“脚本运行成功”。本地检查器发现不兼容变更时也会正常结束；退出成功表示程序完成了检查，不表示接口变更通过。

### 配套示例真正验证了什么

从仓库根目录运行：

```sh
python3 episodes-codex/agent-skills/demo/run_demo.py
```

完整文件位于[本期制作工程的demo目录](https://github.com/linhongcun/video-studio/tree/main/episodes-codex/agent-skills/demo)。`outputs/trace.json`记录实际文件身份、命令和结果，`review.json`与`review-optional.json`分别保存必填及可选分支。

这个程序真实读取文件、启动Python子进程并检查合成契约，但**没有调用LLM或真实HTTP服务**。技能由演示宿主显式选定，四阶段上下文载荷是机制示意，不是实测模型输入，也不能证明模型自动选择技能成功。索引阶段宿主真实读取了两个`SKILL.md`文件，却只把提取的名称和描述放进示意载荷；“模型没有收到正文”与“程序从未读过文件”是不同事实。

本期另保留一次真实Codex子代理按技能执行的记录：它先看候选名称/描述，再选择接口兼容审查，读取入口、规则和输入，实际调用工具运行两个分支，最后提交带范围说明的审查结论。结果在`outputs/agent-review.md`与`agent-review.json`中。它没有读取未选发布说明的正文，也没有把检查脚本源码全文读入模型上下文。这个记录支持**这一次受委派的本地执行**，不等于商业宿主端到端自动技能路由测试，更不是准确率提升实验；`run_demo.py`本身仍没有调用LLM。

字段检查范围也很窄：它只检查简化JSON对象的必填约束，不覆盖响应字段、类型收窄、枚举、认证、默认值、状态码或实际服务行为。可选分支通过这一规则，不能据此称整个API完全兼容；必填分支的拒绝也只是本地校验器结果，不是虚构的HTTP响应。

## 实际价值与使用边界 {#boundaries}

提示词、工具和Skill分别承担不同职责，可以在同一个系统中配合：

| 对象 | 承担的职责 | 本例对应 |
|---|---|---|
| 提示词 | 承载模型接收的指令与任务要求 | 当前审查需求、已读取的工作指引。 |
| 工具 | 提供读取文件、运行程序等执行能力 | 读取字段规则，执行字段检查。 |
| Skill | 将可复用方法与资源组织成可发现、按需使用的包 | 名称/描述、入口指引、参考规则与脚本。 |

同一段说明既可以直接出现在Prompt里，也可以在Skill被选中后进入上下文。两者的内容未必不同，改变的是发现、分发、复用和加载方式；不能把“换成文件”本身当作模型能力提高的证据。[^spec][^client]

### 按需加载不保证全程更省

本地两项短技能的实际UTF-8字节记录如下。它仅描述本例构造的载荷，不是token计量、请求费用或模型效果评测：

| 配置 | 起步的方法载荷 | 加入相同检查结果后的累计新增载荷 |
|---|---:|---:|
| 先名称/描述，再加载选中正文与规则 | 555字节 | 3649字节 |
| 两套方法及字段规则都先放入 | 3025字节 | 3621字节 |

渐进路径起步更小，却在这个小例子的完整路径上多了28字节，因为发现索引与重复元数据也有开销。我们保留这个结果，没有加长无关说明来制造“节省比例”。真实收益还取决于技能数量与长度、被激活的比例、调用次数、缓存及宿主上下文策略，不能从起步载荷较小推出全任务成本一定更低。

### 已加载内容和执行权限仍要管理

“按需加载”不等于“用完自动消失”。内容什么时候继续保留、裁剪或压缩，由宿主管理。例如当前Claude Code文档明确说明技能正文在后续轮次和压缩中的保留机制；它是产品行为，不能推广成所有宿主完全相同的生命周期。[^lifecycle]

方法和规则也要维护版本，脚本会有缺陷，返回结果需要核对。Skill格式不会自动给脚本增加权限，加载成功更不会证明结论正确。标准中的`allowed-tools`仍属实验性支持字段，具体含义和约束必须查所用宿主，不能仅凭文件里的声明推断实际授权。[^spec]

与MCP的区别也不宜压成“一个只教方法、一个只给工具”。Skill定义内容包怎样组织，MCP解决能力与资源的协议交互，现有可选Skills over MCP扩展还能承担技能发现与获取。读取资源、激活技能和执行脚本仍是不同环节，实际支持要逐宿主核验。[^mcp]

回到开头：Markdown是入口，配套资料与脚本承载方法的细节，宿主让它们可发现、可按需读取或执行。值得复用的是这套工作方法及其可核对的依据。
