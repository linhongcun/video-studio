本片只回答：任务已经受理，为什么还没完成？以订单7042的同一后台处理任务贯穿“提交→保存并排队→暂停等待→恢复处理→业务完成→页面查询结果”。随后区分短时高峰可以排空与持续流入快于完成会积压。

- 01/09为订单功能交互示意，展示提交按钮、订单身份与状态；不套浏览器地址栏、DevTools或无关窗口。教学透视从同一7042展开，不声称还原任何真实平台内部架构。
- 网站服务生产消息，页面不直接连接Broker；后台消费者执行任务。RabbitMQ只标记消息中间件身份，产品图标不替代内部状态。
- 示例采用durable、non-exclusive、non-auto-delete的quorum队列、持久消息、发布确认及手动消费确认。配置细节留图文，片中只说明已保存前提，不展开发布确认协议。
- 消费者暂停发生在尚未取走7042之前，消息仍为ready待处理；恢复后首次接收同一7042。无断连重投、确认丢失或幂等实现支线。
- 业务结果先成功保存，再向队列手动ACK；ACK只结束投递。页面经网站服务查询业务结果后显示完成，不接收“ACK直接回页面”的假链路。
- 流量、单次处理节奏和2入1出为教学示例，不是产品性能基准。队列容量有限，等待与积压是缓冲的代价。
