## 一手资料核验

已通过联网工具实际读取 MySQL 8.4 官方手册正文：

- [autocommit, Commit, and Rollback](https://dev.mysql.com/doc/refman/8.4/en/innodb-autocommit-commit-rollback.html)，§17.7.2.2：默认自动提交下，各条语句各自形成事务；可显式把多条更新组织为一笔事务。提交确认本次修改，显式回滚撤销本次事务修改。片中的反例应称“两步分别生效”，不要声称 InnoDB 完全没有事务。
- [InnoDB Error Handling](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)，§17.20.5：错误的回滚范围依情况而定，有些只撤销失败语句。第二步失败后，应画出应用决定并请求回滚整笔，而不是宣称任意 SQL 错误必然自动撤销整个事务。
- [InnoDB Recovery](https://dev.mysql.com/doc/refman/8.4/en/innodb-recovery.html)，§17.18.2 的 Crash Recovery：数据库进程异常退出，重启恢复会撤回当时尚未提交的事务。不能把“提交前崩溃”扩写为“提交后回包丢失必然回滚”，也不能把该过程说成金融系统对任意故障的保证。
- [Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)，§17.7.2.3：一致性读基于快照，不读取未提交修改；同一事务能读到自己的先前修改。因此“本次待提交修改预览”和“已确认余额”必须清楚区分，不能让观众以为别人已经看到未提交扣款。

## 配音包络诊断（不等于读音识别）

根代理发现03、16镜首句take a的尾巴裁切时长异常，委托检查。已使用共享`common.cut`及FFmpeg `silencedetect`核对：03-a、16-a在最后一段明显声音之后仍有较长静音和极短尾噪，共享裁切落在该段之后，存在把附加尾句留在选择片段中的风险；建议重新生成take，不改变共享起音算法。16-b的尾段与主句间隔可独立分开，形态较正常。05-a句内约0.80秒低声间隔也已提示重生成比较。以上只说明波形和裁切区间，未声称识别出了具体汉字或完成听辨。

最终选段追加复核：03-B共享裁切长度6.75秒、独立尾段0.391秒，选中片段最后主声后约0.209秒静音收尾，未见A的疑似附加尾声保留形态；FFmpeg -40dB低声间隔最长约0.405秒。05-B最长约0.204秒，原05-A约0.80秒长间隔已消除；16-B最长约0.237秒，独立尾段0.428秒。三句最终均选B。以上仍是声学诊断，不替代逐字识别或完整听辨。
