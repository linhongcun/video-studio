# EP.16 重制：扣了钱，对方没到账？

- 对应 issue：#67；2026-10-24（北京时间）。用户要求从 issue 选择下一集继续制作，本稿为本地观看版；不修改已上线旧版，不发布。
- 主线：同一数据库内的一笔教学转账，扣款与入账放在同一笔事务，成功提交共同确认，未完成时撤销整笔修改。旧版包裹／封箱比喻废弃。
- 画面：第二版按 visual-direction-v2.md 重做。16 镜全 canvas，深色共享页身、单一舞台与大号数字，一次只引入当前所需对象，非当前信息退出或退为上下文。用操作路径、焦点平移、共同落位和撤除过程讲解。无假应用窗或实物比喻；小型品牌和示例说明固定，正文说明按需出现。
- 示例数据：你的账户 1000 元，对方 500 元，转账 200 元；成功结果为 800／700，撤销后为 1000／500；无事务合并的半成结果是 800／500。数字不必口播；常驻「示例数据 · 同一数据库内 · 非真实银行流程」。
- 状态逐步揭示：当前修改用大号金色预览，原确认余额只保留简洁锚点；焦点随扣款、入账移动，提交时共同进入确认位置，撤销时移除本次修改。预览是当前事务看到的状态，不表示别的会话已读到，也不对应内存/磁盘物理分层。
- 术语只有「事务」「提交」「回滚」，首次命名在镜 06、09、11，均在句首；标签在实测起音处出现并保持至少 63 帧。DevTools 与代码画面 0 处。
- 镜 10 是从相同原始余额开始的另一笔示例，不是把镜 09 已提交的转账撤销；镜 12 也是另一个未提交的示例。
- 错误边界：镜 10、11 明确是应用发现错误后请求整笔回滚，不声称任意语句错误都会自动回滚整笔。镜 12、13 只讲提交前数据库进程崩溃及正常重启恢复；不讲提交结果不明、跨行支付、介质毁坏或分布式事务。
- 技术背景为 MySQL 8.4.0 所属长期支持系列的 InnoDB；片中数据库指具备这些事务能力的示例，产品名、版本、ACID、自动提交、脏读及存储恢复细节只进文章。公开正文已实际核验，见 research.md。
- 时序以真实配音及可获得的声学分析为准；没有 ASR 时如实标识句级边界，不能编造逐字对齐或识别覆盖率。
