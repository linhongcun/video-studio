## 先看题目要什么 {#problem}

LeetCode第739题给出按日排列的整数气温`temperatures`。对于每一天，找到**未来第一个气温严格更高的日子**，返回要等待的天数；未来没有这样的日子，则该位置返回`0`。输入有`1..100000`天，气温整数范围是`30..100`。[^problem]

这是为原来的每一天各算一个答案，既不是找整段最高温，也不是返回升高了几度。相等温度不算更暖。片中自选教学示例是：

```text
第几天： 1   2   3   4   5   6   7   8
气温值：33  34  35  31  30  32  36  33
等几天： 1   1   4   2   1   1   0   0
```

第3天的35，要等到第7天的36才第一次更暖，答案是`7 - 3 = 4`天，温差1不是答案。第7天和第8天都没有未来更暖的一天，答案为0。

这里的气温是满足题目约束的构造示例，不是真实天气预报。官方题面未指定温度单位，本片也不擅自添加摄氏或华氏符号。画面标“第1天”，程序下标从0开始：同一对日期同时减去1，下标差与日期差相同。

## 从重复查找到保留等待 {#derive}

### 先决定保存什么，再选择工具

直接做法是对每一天从下一天起往后查看，遇到第一个更高温度就停止。它能得到答案，但相邻日期会反复查看同一段未来。例如第3天往后看第4、5、6、7天，第4天又要看第5、6天。

可以反过来按日期向前走，让新来的一天处理尚未得到答案的旧日子。需要保存的是**未解决日期的下标**，这样有两项信息可以随时得到：通过原输入查询旧气温，用当前下标减去旧下标计算等待天数。

接着决定检查顺序。较凉的新日子暂时不能解决旧日子，就把自己的下标放在末尾。这样留下的气温从早到晚不升，例如第3、4、5天留下的是`35 ≥ 31 ≥ 30`，最近的30在末尾。

新来32时，先解决最近的30，再解决31；遇到35时停止。若当前气温连末尾都不比它高，更早留下的气温只会更高或相等，也都不能被当前天解决。这给出“从末尾开始、满足条件就移出、否则停止”的操作。

具有这种温度顺序的后进先出结构，就是本片采用的**单调栈**。栈里保存下标，比较的是下标所对应的原气温，不对输入排序。排序会破坏日期的先后关系。

## 按天走完整过程 {#walk}

下面表格是执行过程的文字复查。视频用连续气温线和原日期位置表达比较及等待跨度，辅助区只保存尚未解决的日期。

| 新到的日期 | 当天气温 | 如何处理待解决的天 | 本轮新写入的答案 |
|---|---:|---|---|
| 第1天 | 33 | 开始为空，没有旧天可比较；加入第1天 | 无 |
| 第2天 | 34 | 比第1天更暖，移出第1天，再加入第2天 | 第1天等1天 |
| 第3天 | 35 | 比第2天更暖，移出第2天，再加入第3天 | 第2天等1天 |
| 第4天 | 31 | 比末尾第3天凉，停止，加入第4天 | 无 |
| 第5天 | 30 | 比末尾第4天凉，停止，加入第5天 | 无 |
| 第6天 | 32 | 依次移出第5天和第4天；遇到第3天35后停止，加入第6天 | 第5天等1天；第4天等2天 |
| 第7天 | 36 | 依次移出第6天和第3天；栈空后加入第7天 | 第6天等1天；第3天等4天 |
| 第8天 | 33 | 比第7天凉，停止，加入第8天 | 无 |

日期走完后，第7天和第8天仍在等待。答案数组最初全是0，只在找到更暖日期时改写，所以这两个位置自然保持0。

### 相等为什么必须保留

另一个输入`[30,30,31]`需要独立从头执行。第2天的30与第1天相等，不算更暖，因此不能移出第1天。第3天31出现，先解决第2天，等待1天；再解决第1天，等待2天，结果是`[2,1,0]`。

所以条件写严格大于`>`，不能写`>=`。保留相等温度也说明栈内气温是**不升**，并非要求所有相邻值严格下降。

### 为什么得到的是第一个

考虑任何还在等待的旧日期`previous`。按日期扫描到`today`之前，所有中间日期都没有让它得到答案；否则它已经移出待解决区。现在`temperatures[today]`第一次严格更高，就立即写入`today - previous`，所以这个等待时间是最短的。

停止比较也不会漏掉能由当前天解决的日期：末尾是待解决区中气温最低的候选之一，当前天连它都不能超过，就更不能超过前面更高或相等的气温。将当前天加入末尾后，不升关系继续成立。初始为空也满足这一条件，由此每一天都维持同一个规则。

## 写回原位与复杂度 {#code}

下面是本片唯一执行源`solution.py`的完整内容。片尾由同源`solution.json`显示固定字号代码，静态停留5秒并提示暂停。

```python
class Solution:
    def dailyTemperatures(
        self, temperatures: list[int]
    ) -> list[int]:
        answer = [0] * len(temperatures)
        pending = []
        for today, temperature in enumerate(temperatures):
            while pending and temperature > temperatures[pending[-1]]:
                previous = pending.pop()
                answer[previous] = today - previous
            pending.append(today)
        return answer
```

- `pending`保存未解决日期的下标，`pending[-1]`是最近留下的日期。
- `while pending`先确认有旧天，空时不访问末尾。
- 严格更暖才`pop`，随后用下标差写回旧位置。
- 不够暖就停止这次`while`，再加入今天；原始气温数组不变。

一个日期可能一次解决多天，但每个下标只加入一次，最多移出一次。因此所有循环合计`O(n)`时间，待解决下标最多`n`个，额外空间为`O(n)`；输出数组另需`O(n)`空间。这里按Python列表末尾追加/移出的通常均摊成本模型计算，未将复杂度等同于某台机器的秒数。

本期使用独立的二重循环oracle验证全部输出，包含三个官方样例、相等和递减边界、21844组小范围穷举、3000组确定随机与两组十万长度输入。动画中的compare/pop/resolve/push/finish状态来自对上述函数的真实执行追踪；这些检查支持算法与源数据一致性，不等于学习效果实验。
