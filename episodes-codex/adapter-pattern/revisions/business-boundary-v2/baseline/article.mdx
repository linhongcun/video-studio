## 先看一次发货提醒 {#why}

商家打开十七号订单的详情。订单已经发货，需要给买家提交一条发货提醒：

| 本次教学示例 | 内容 |
|---|---|
| 订单 | 17，已发货 |
| 收件人 | `buyer17@shop.example` |
| 提醒正文 | 订单17已发货 |
| 页面操作 | 发送发货提醒 |
| 提交后的页面结果 | 已受理 · 等待送达回执 · Q17 |

点击后，页面显示“已受理·等待送达回执”。界面和通知服务都是**教学模拟，不发送真实消息**，没有核验某家商用产品的内部架构。Q17是本例受理编号，不是送达凭据。

接入一个新服务时，常见障碍是：**它有需要的能力，使用方式却和业务方要求的约定不一样。** 本例业务方提供收件人和提醒正文，需要取得提交后的受理结果；新服务接受另一种参数组织，也用自己的状态表达结果。

先区分两个视角：**接入服务时的开发视角**用于分析约定差异、安排结构；**结构接好后的运行视角**用于跟踪一次请求。后文沿开头同一次提交看去程与回程，没有再次发送提醒。

### 两边到底哪里对不上

具体字段与名称在这里复查，视频正文只用中文说明职责：

| 业务方需要的目标约定 | 已有服务自己的约定 |
|---|---|
| `send(recipient, text)` | `deliver(Payload(target, body))` |
| 收件人、提醒正文两个业务输入 | 接收目标、消息内容的服务参数对象 |
| `Submission(ACCEPTED, reference)`或明确拒绝 | `RawReceipt("QUEUED", ticket)`或`REJECTED` |
| 技术失败/无法确认时显式失败 | 服务可能抛通信异常，也可能返回未知/无效状态 |

在本例中，左右两边都能完成**提交消息并报告受理情况**，但不能直接混用格式或结果。适配器解决的是这种使用约定的不兼容，不是替服务创造新的消息能力。官方Spring的适配器源码和OpenJDK的接口适配例子，都能看到“按目标接口使用已有对象，再把工作委托过去”的设计关系。[^spring][^jdk]

## 从同一对象展开结构 {#roles}

把刚才的产品对象对应到结构，逐个看职责：

| 角色 | 本例名字 | 负责什么 |
|---|---|---|
| 业务方（Client） | `ShipmentReminder` | 按自己的通知约定提交订单17的发货提醒 |
| 目标约定（Target） | `Notifier` | 规定业务怎样提交，以及受理结果/失败的含义 |
| 适配器（Adapter） | `NotificationAdapter` | 履行目标约定，持有已有服务，转换请求与返回并委托执行 |
| 已有服务（Adaptee） | `VendorSdk` | 按自己的参数和返回规则处理请求 |

`VendorSdk`表示假想供应方原本的约定；`FakeVendorSdk`只是为了本地教学而做的替身。它没有网络调用，也没有真的给买家发送消息。适配器没有把目标接口强加到供应方接口上。

这里采用的是**对象适配器**：适配器持有现有服务对象，接到业务调用后再委托它。这个选择不意味着所有适配器模式都必须采用同一种语言写法或同一种持有形式。[^spring][^jdk]

本例目标约定的业务含义始终是“提交提醒，取得受理结果”。如果一开始要求的是“保证买家已经收到”，而服务只能排队受理，就不是仅靠格式转换能够满足的约定。

### 去程：转换以后，还要真正委托

业务方按`Notifier`约定提交收件人和正文。适配器把`recipient`对应到`target`，把`text`对应到`body`；值仍是同一地址和“订单17已发货”，没有交换、截断或暗中改写。

随后适配器调用它持有的`VendorSdk`。转换不是把字段改个名后就宣布结束：**实际提交的工作仍交给已有服务。** 本例源码用教学替身执行这次调用，没有真实外发。

### 回程：结果的格式与含义都要对应

服务的模拟回执是`QUEUED`、`ticket=Q17`。按本例服务约定，它表示已经接受提交、后续处理尚未完成。适配器将它转为`Submission(ACCEPTED, "Q17")`，业务方才有依据让页面显示“已受理 · 等待送达回执”。

| 位置 | 同一次提交的可观察结果 |
|---|---|
| 模拟服务返回 | 已排队，受理编号Q17 |
| 适配器返回业务 | 已受理，原编号Q17 |
| 产品页反馈 | 已受理 · 等待送达回执 |
| 目前不能推出 | 买家已经收到提醒 |

“已排队”是教学SDK回执约定的意义，不表示这段本地程序真的创建了消息队列或后台投递任务。RFC9110的202状态也明确区分接受处理与完成，甚至指出请求最终可能不被执行；这里用它核对语义边界，**没有声称教学SDK使用HTTP202**。[^http202]

## 转换的收益与边界 {#boundary}

### 不把未知翻成确定结果

主链受理完成后，视频用短规则说明另外两种边界，未再发一条消息：

- 服务**明确拒绝**时，本例返回业务拒绝，不返回已受理。
- 技术异常、超时、未知状态或无效回包，都可能让业务方**无法确认是否已受理**。不能吞掉异常后伪装成已受理，也不能一律当作确定拒绝。

例如，服务可能已经记录了请求，回包时却发生通信问题。调用方没拿到结果，不等于服务没有接到请求。本例用`SendFailure`把“没有确认结果”交给调用方，并保留原技术异常原因；**不会自动重试**，也不承诺撤销、去重或恰好一次投递。这些是本例的明确选择，需要具体实现，不能仅凭“使用了适配器”就获得。[^demo]

服务如果没有送达确认能力，把`QUEUED`重命名为`DELIVERED`并不会产生一份送达事实。额外回执查询或可靠投递机制需要另行设计；本片不将它们塞入主线。OpenJDK的接口适配例子也显示：适配以后，底层没有提供的某些操作仍可能明确不支持。[^jdk]

### 哪些变化留在适配器，哪些还得改

共同业务约定保持不变时，外部服务的入参、返回状态和失败表达可以集中在适配器里处理。本例的`ShipmentReminder`本来就按`Notifier`写好，不需要理解SDK的参数对象和原始状态。

但这不等于项目零改动。新的适配器需要实现和测试；**创建对象、把适配器接给业务方、选择服务和填写配置**的位置仍要调整。若业务目标或消息含义改变，也应重新评估目标约定，不能为了宣称“调用方不改”而改变结果承诺。

如果双方约定已经一致、直接使用服务足够清楚，适配器未必值得增加。引入它以后，还多了一层需要阅读和维护的转换，应测试入参、已知返回以及失败/未知边界。选模式是为了处理真实的不兼容关系，不是为每个服务都增加一个包装。

### Java关键代码与完整程序 {#java}

片尾给出5秒独立静默卡，提示“暂停查看”和“关键节选”。以下与卡片同源，连接结构角色与一次使用；**它省略了完整程序的外围定义，不能单独复制就运行**。

```java
interface Notifier { Submission send(String recipient, String text) throws SendFailure; }
static final class NotificationAdapter implements Notifier {
    private final VendorSdk sdk;
    NotificationAdapter(VendorSdk sdk) { this.sdk = Objects.requireNonNull(sdk); }
    public Submission send(String recipient, String text) throws SendFailure {
        requireInputs(recipient, text);
        try {
            RawReceipt raw = requireReceipt(sdk.deliver(new Payload(recipient, text)));
            return switch (raw.status()) {
                case "QUEUED" -> new Submission(Status.ACCEPTED, raw.ticket());
                case "REJECTED" -> new Submission(Status.REJECTED, "");
                default -> throw new SendFailure("受理结果未确认：未知回执状态");
            };
        } catch (VendorFailure ex) {
            throw new SendFailure("受理结果未确认：SDK通信异常", ex);
        }
    }
}
// main内：SDK为教学模拟，不外发
Notifier notifier = new NotificationAdapter(new FakeVendorSdk());
Submission result = new ShipmentReminder(notifier).send("buyer17@shop.example");
```

完整源见[AdapterDemo.java](https://github.com/linhongcun/video-studio/blob/main/episodes-codex/adapter-pattern/demo-java/AdapterDemo.java)，验证入口见[verify.py](https://github.com/linhongcun/video-studio/blob/main/episodes-codex/adapter-pattern/demo-java/verify.py)，实际[编译运行记录](https://github.com/linhongcun/video-studio/blob/main/episodes-codex/adapter-pattern/demo-java/verified-results.json)保留了源码SHA、卡片逐行映射与12组行为检查。此次使用OpenJDK21，未作真实消息外发。[^demo]

`FakeVendorSdk`是教学替身，不能用它的确定返回证明真实网络不会超时。完整验证覆盖明确拒绝、服务受理后丢失回包、原始异常保留、空/未知回执、受理编号缺失、非法输入、精确字段传递、独立重复调用和业务方仅依赖目标约定等，范围以实际报告为准。

阅读已有项目时，可以寻找：业务方需要的目标契约是什么、已有服务的契约哪里不同、谁负责转换、是否真正委托原对象、结果和异常是否保留业务含义。只有一个名叫Adapter的类，或只看到一层包装，都不足以代替这些关系。
