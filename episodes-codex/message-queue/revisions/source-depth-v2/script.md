# 订单已提交，为什么还没处理完？

身份：保留EP.10 / message-queue / Kafka MQ01 · 入门及原题、首发身份和旧封面。本轮独立source-depth-v2制作输入，旧工程与冻结记录保持。

唯一问题：任务为什么可以先被Kafka存起来，再由消费者执行，因此“已受理”还不是“已完成”。

核心因果必须在正文兑现：同一E01任务数据→序列化字节→生产者本地发送缓冲→Broker按P0日志末尾分配offset并追加字节（不调用通知业务）→消费者带position发Fetch→客户端解码并推进position→应用另执行通知并保存业务完成→页面查询业务结果。本轮只展开存储和执行的分离，不详细讲Sender批次/在途（MQ04）和committed恢复（MQ03）。

固定示例：orderId=7042，eventId=E01，task=notify-order；orders主题只有P0，compression.type=none，StringSerializer/StringDeserializer UTF-8，显式指定P0。开始日志空，分区logEndOffset=0；网站按本例发送成功后才回已受理；通知消费者起始position=0，enable.auto.commit=false，max.poll.records=1，暂停期间不执行通知业务。Kafka4.4.0/Java客户端，固定commit1156b2752aaa28eafc0b4c4d387e63356793268d；acks=all和生产幂等开启，本例RF1/minISR1，只用于机制教学，不作高可用保证；副本机制不进正文支线。

视觉约定：沿Kafka style-v1暖炭灰/橙/冰蓝，4:3安全与字幕边界同现行制作规范。首屏是真实功能语义的教学页面：订单提交、受理反馈、通知状态；不把机制图放浏览器壳。由同一E01从功能界面展开内部结构：左侧网站及发送缓冲，中部P0日志（先简明记录，再局部展开字节），右侧消费者程序（读取与业务两个区）。记录原件追加后保留原位，取数用副本表达；读取位置1和业务已完成显示在不同容器。主体动作按实际句级起音设计，结果标签只在动作完成后出现。

术语随对象解释，不念源码方法名。编码字节可展示模型实际生成的UTF-8前缀，注明内容示意，不能伪造完整Kafka二进制格式；日志段文件追加不等于每条立即fsync，不画磁盘落盘保证。Broker的日志追加路径从logEndOffset取得下一编号、无压缩验证器分配编号后append和末尾更新，正文用同一记录/编号动作解释；原方法名、完整调用链和永久行号留研究/文章。

### 01 problem

旁白：你提交订单7042，页面已经显示已受理，通知却还在等待。请求既然成功了，后台为什么还没做完？

源码对照：本例网站策略与业务状态，Kafka实现依据见research.md。

### 02 split

旁白：回看这次提交，它分成两件事：留下待处理的任务，再执行通知。Kafka保存前一件事的内容，消费者程序负责后一件事。
画面：功能页面展开两步总览，保留订单7042；存储任务与执行业务分开，先不堆内部细节。
源码对照：KafkaProducer.doSend、Broker append链、消费应用边界。

### 03 event

旁白：网站先为通知生成一条事件，里面写着订单7042和要执行的任务。它是一份任务数据，不是一段交给Kafka运行的业务程序。
画面：从订单提取同一E01数据卡，字段eventId/orderId/task，业务程序仍在消费者侧尚未执行。
源码对照：ProducerRecord的key/value输入，序列化与Broker记录路径；task字段为明确教学数据。

### 04 encode

旁白：发送之前，网站把这些字段编码成字节，才交给客户端的发送缓冲。同一条事件暂存在本地，后台再把它发到指定分区。
画面：同一数据卡局部展开UTF-8实际字节前缀；先入生产者本地缓冲，再出发P0，固定E01身份。
源码对照：KafkaProducer.java1080–1111，StringSerializer.serialize。

### 05 append

旁白：Broker收到记录，不去调用通知业务，而是把它追加到分区日志的末尾。本例日志原来为空，追加后这条记录的位置编号就是零。
画面：P0当前末尾0→待写记录分配位置0→追加落位；通知应用区保持暂停，业务代码没有被Broker调用。
源码对照：UnifiedLog.logEndOffset→LogValidator分配offset→LocalLog.append。

### 06 stored

旁白：日志段文件里保存的是编码后的记录，分区末尾随之向后移到一。即使通知程序此时没有运行，这条记录也已经能留在Kafka里。
画面：局部展示日志段的记录头/内容示意和实际字节长度；endOffset0→1，E01原位；业务执行暂停但存储已完成。
源码对照：LocalLog.append后updateLogEndOffset，FileRecords.append真实写通道；不宣称立即fsync。

### 07 accepted

旁白：收到本例写入成功的响应后，网站就能把任务已受理回给页面。这里确认的是任务已经留下，不代表通知已经发出。
画面：从日志回传发送成功，再回用户页面已受理；通知仍待处理。导航回总览定位读取阶段。
源码对照：生产确认配置与网站策略；消息存储不等于消费业务完成。

### 08 fetch

旁白：接下来消费者发起拉取，带上自己下一条准备读取的位置。本例从零开始，所以Kafka返回位置零这条记录，原日志仍在原处。
画面：恢复消费者，Fetch请求明确携带P0/0；同一日志记录副本沿返回路径抵达，源记录不移走。
源码对照：AbstractFetch.prepareFetchRequests把position.offset装入FetchRequest；记录读取不删除日志。

### 09 decode

旁白：客户端把记录里的字节解码，应用又能读出订单7042这些字段。客户端把下一读取位置从零改成一，再把这条记录交给应用处理。
画面：副本字节先由StringDeserializer解码回文本，再由应用解析原E01字段；读取位置0→1先更新，再交应用待执行区，业务状态仍待处理。
源码对照：CompletedFetch.parseRecord/nextFetchOffset，FetchCollector.subscriptions.position，ClassicKafkaConsumer.poll返回。

### 10 execution

旁白：注意，这个一只表示下次读哪里，不表示通知已经完成。真正发出通知，还要由消费者里的业务代码，另行调用通知功能。
画面：突出position1与业务待处理不同容器；记录进入应用处理函数，通知功能调用单独出现。
源码对照：客户端position为读取进度；通知应用是本例单独定义的处理程序。

### 11 completed

旁白：现在程序执行这条任务，通知结果从等待变成完成，并保存到业务状态里。原来的日志仍然保留这条记录，业务完成状态在另一处更新。
画面：应用完成动作、保存E01完成；P0记录依然存在、末尾1与读取位置1不随业务完成跳变。
源码对照：本例应用状态机与Kafka日志分离，非Kafka自动执行业务。

旁白：页面再次查询业务状态，读到这项任务已经完成，这时才显示通知成功。页面查的是业务结果，不能只看Kafka里有没有记录，就显示全部完成。
画面：沿查询路径读本例业务结果、回页面完成；回指日志记录与独立业务完成状态的不同容器，不追加条件倒放。
