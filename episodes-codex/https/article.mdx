跟随一次示例登录，演示明文传输的风险，以及HTTPS怎样用身份核验、加密和完整性保护传输；同时说明加密不等于网站可信。

## 先看没有加密的情况

先看没有加密保护的示意。请求内容原样经过网络，能够观察这段流量的人，就可能读到其中的信息。

## 看见以外，还可能被动手脚

问题不只是被看见。传输缺少可靠保护时，内容还可能被替换，接收方却难以发现。

## 给传输加上保护

HTTPS，在网页通信外加上安全传输保护。但在发送密码之前，还得先确认：对面真是这个域名的网站吗？

## 网站先出示证书

证书，把网站的公钥和域名等身份信息联系起来。浏览器会检查证书是否适用于这个域名，是否有效，以及信任关系。

## 核验不过，不能当成正常连接

如果证书不匹配或不被信任，浏览器会发出警告。随手忽略警告，可能破坏原本要建立的身份保护。

## 握手，共同建立传输保护

在握手过程中，双方会协商保护连接所需的密钥，也完成必要的身份核验。密钥不会作为普通明文直接放在网络上发送。

## 这次，密码先变成密文

现在，登录请求先加密，再经过网络。中间观察到的是密文，网站这一端才能还原并处理请求。

## 返回的数据，也受到保护

网站返回的页面内容，同样通过受保护的连接传输。保护发生在双方之间的传输过程。

## 被篡改的数据，不该照常接受

完整性保护，让接收方能发现传输数据被改动。验证不过的数据会被拒绝，而不是悄悄当成正常内容。

## 传输安全，不等于网站可信

不过，加密连接不代表网站卖的东西靠谱，也不代表网站不会滥用你交出的数据。密码到达网站以后，已经离开这段传输保护的边界。

## 适用边界与来源

本次于2026-10-25（北京时间）核对以下负责工作组或MDN官方仓库的固定正文；各项分别提供正式链接与本轮实读版本，便于核查。

**[R1] IETF TLS WG：《The Transport Layer Security (TLS) Protocol Version 1.3》（RFC 9846 · 2026）**。握手协商密钥并完成认证；TLS 1.3记录使用AEAD解密并验证；验证失败时拒绝记录并终止连接；握手内部并非先完成证书再开始全部密钥交换。实读章节：§2 Protocol Overview；§4 Handshake Protocol；§5.2 Record Payload Protection。

[正式链接](https://www.rfc-editor.org/rfc/rfc9846.html) · [本轮实读的固定正文](https://github.com/tlswg/tls13-spec/blob/c728b4efb4c12159371279227df6464541eafb58/rfc9846.md)。

**[R2] IETF HTTP WG：《HTTP Semantics》（RFC 9110 · 2022）**。HTTPS客户端须核验服务身份与目标源站是否匹配，证书核验用于防冒充。实读章节：§4.3.4 https Certificate Verification。

[正式链接](https://www.rfc-editor.org/rfc/rfc9110.html) · [本轮实读的固定正文](https://github.com/httpwg/http-core/blob/3cdfb4df4dc47e75e9642efc99ab699a0495d883/rfc9110.xml)。

**[R3] MDN Web Docs：《Transport Layer Security (TLS)》（持续维护文档 · 2026-10-25核验）**。TLS提供传输中的保密、完整性与认证；网站证书将公钥关联到域名；这些保护面向客户端与服务端之间的连接，不作为商品信誉或服务端存储安全的保证。实读章节：TLS概览的Encryption／Integrity／Authentication；TLS handshake；Server authentication。

[正式链接](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Transport_Layer_Security) · [本轮实读的固定正文](https://github.com/mdn/content/blob/c49748a0ce4fdf77427e29cb6edbca8953a514e7/files/en-us/web/security/defenses/transport_layer_security/index.md)。

TLS工作组本轮实读正文头部明确列出RFC编号9846、日期2026-07以及替代8446的关系；MDN中的版本号文字不作为最新RFC编号的证据。

[RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)（2018，仅参考；原访问日期2026-10-24）保留为原稿的历史来源，当前片尾与本次机制核验以RFC9846固定正文为依据。

本片按理解顺序分解身份核验与密钥协商，并非TLS消息的逐条时序；传输保护以端点及密钥未失陷、身份验证成功为前提，不表示商品信誉或服务端存储安全已获保证。
