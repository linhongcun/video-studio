# Skills的视觉主线与内容价值审稿

当前文稿为12镜24句、4章。目标约150–180秒，最终以正常语速的真实配音与完整信息量核对，不靠加速或固定时长倒推。唯一任务是开发者审查同一次创建订单接口变更，旧请求有sku与quantity，新版定义新增必填channel。画面以「方法如何抵达Agent」为主要变化，不把接口调用或通用Agent循环再拍一遍。

## 一眼能看懂的入口

首帧直接给对应审查功能对话、具体字段变更及Skills标题。用户输入询问旧客户端兼容性；画面先保留问号。不要先铺一整页生态名词、展示陌生模块框或先宣布有Skill必定正确。两份证据中的业务对象持续一致，不能中途换成退款审批。

## 稳定对象与空间

- 上方保留同一次审查需求与字段变更的轻量定位，不做持续运动的装饰导航。
- 外部技能包在左，当前上下文在右，宿主工具执行区域在下。进入局部时保持小型定位关系，片尾收回整体。
- 02与03是两种初始组织配置的对照：03必须标「换成技能组织时 · 另一套初始配置」，从同一任务重新开始，不将02里已读正文画成自动卸载。技能配置的发现阶段只有名称/描述进入上下文，完整说明保留在包中；选中展开时说明卡从包到上下文，外部原件仍存在。
- 参考资料经「读取」路线进入上下文；脚本走「执行」路线到宿主工具，返回结果再进入上下文。脚本源码并非必须先装进模型，不能把两条路径画成同一条读取箭头。
- 固定暖色表示当前需要的内容，低对比表示暂不读取的内容；所有身份有文字，不只靠颜色。不要把不相关资料画成被删除，或把当前上下文当成磁盘存储。
- 当前上下文中已读指引、规则和结果在后续镜头继续有对应，11镜不清空。保留/裁剪/压缩是宿主策略，没有本片承诺的自动回收时点。

## 逐镜必须看见的增量

| 镜 | 观众新增理解 | 可观察因果 |
|---|---|---|
| 01 | 要审查哪个真实开发问题，为什么关心技能文件 | 创建订单新增必填channel；旧请求仍只有sku/quantity；审查问号 |
| 02 | 方法全常驻存在输入取舍 | 接口审查与发布说明两份正文进入当前上下文，本任务只需接口审查 |
| 03 | 技能可先被发现而无需先读全正文 | 另一套初始配置中正文留在包内，仅名称/描述成为候选条目 |
| 04 | 描述承担路由信息，也会有歧义 | 精确适用条件对应需求，泛描述仅显示潜在歧义，不伪造实测失败 |
| 05 | SKILL.md是可读取的任务指引 | 入口正文进入上下文，没有模型权重变化或自动执行 |
| 06 | 资料与脚本用途不同 | 全局两路先静态停留，随后才分别讲解 |
| 07 | 参考资料按任务需要读 | 只将请求字段规则送入上下文，未选发布说明正文保留未读 |
| 08 | 预写代码可通过工具运行，模型收结果 | 脚本与旧定义/新定义/旧客户端请求三个输入→工具→结果；源码不走读取箭头 |
| 09 | 任务结果应能回查依据 | 同一字段变更、规则、检查结果组成结论，不把加载成功当成完成 |
| 10 | Skill、指令与工具分工可组合 | 原对象上逐个命名，不新建脱离任务的术语表 |
| 11 | 渐进加载有发现索引开销、维护与正确性边界 | 名称/描述的索引开销可见，小包未必更省；资料版本与证据入口继续可见，不自动清空 |
| 12 | 回答开头：入口背后是可发现、可按需使用的方法包 | 回到同一开发者与结论，收束完整组织关系 |

## 场景、代码和字幕边界

正文只允许两处代码画面：01字段差异和05入口节选；目录节点、证据卡不能伪装成文件管理器或IDE。机制图使用全屏canvas。字段差异只保留当前sku/quantity/channel，入口只突出name/description及三条指引，不整页堆YAML。全部术语首次出现留足可读时间；字幕在相机外层，不被图表、连线或缩放覆盖。
