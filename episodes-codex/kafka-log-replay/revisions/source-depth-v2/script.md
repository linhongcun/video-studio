# Kafka日志重放：消息读过了，为什么还能重读？

版本：MQ03 / EP43 / source-depth-v2；先审稿，尚未配音。

唯一主机制：持久恢复值 → 客户端内存读取位置 → Fetch请求起点 → 同一日志字节。

固定Kafka/Java客户端4.4.0，传统classic consumer group，group.id=notify，orders/P0单分区单消费者，enable.auto.commit=false，max.poll.records=1，非事务、无压缩的单记录批次，cleanup.policy=delete、分层存储关闭。初始committed=0是本例预先已有的保存值，不是无历史组的默认值；position=0。E01唯一命名业务事件，offset0。正常读取推进position=1而不提交；退出抛弃整个旧实例/position；重启查committed并创建新position。

画面：旧封面沿用；正文沿不可变Kafka style-v1。Broker日志文件区、客户端内存区、组恢复值持久区三列稳定，各值的所有者明确。日志字节示意不宣称实际二进制编码或测量；单记录批次让切片与E01可直接对应。恢复的两步源码分别标实际文件/函数，只有真正执行赋值后position才出现0。Fetch箭头读客户端当前值而非直接连committed到日志。committed=1反例明确回到“刚读完、还没提交”的共同状态，只改变提交成功条件；retention反例从原数据仍保留的共同前提切换，旧封闭段先滚动形成，再满足保留/高水位等前提清理，旧字节退出后位置0不合法。无CLI假输出，所有示例是官方实现约束的有限模型，不是Broker实测。

实际依据（正文代码画面总计两处，仅07恢复赋值和08请求参数；04加一和03日志切片用图上动作表达，不另开代码画面，完整片段放文章）：CompletedFetch.java `nextFetchOffset = lastRecord.offset() + 1;`；SubscriptionState.java/seekValidated的 `this.position = position;`（ConsumerUtils.refreshCommittedOffsets先从committed构造position）；AbstractFetch.java使用 `position.offset` 作为FetchRequest.PartitionData实参；LogSegment.read实际 `log.slice(startPosition, fetchSize)`。不将短注释/API合同替代执行链，不展示全套组协调或稀疏索引算法；主动seek和索引细节留文章。
